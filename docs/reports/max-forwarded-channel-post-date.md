# Диагностика даты публикации пересланного поста MAX

**Задача:** `MEMOLY-MAX-FORWARDED-CHANNEL-POST-DATE`

**Статус:** `OBSERVED_API_LIMITATION_CONFIRMED` — для проверенной цепочки пересылки.

**Результат для пользователя:** `NOT_FIXED_AUTOMATICALLY`
**Дата:** 2026-10-17

## Вывод

В проверенной цепочке «человек → канал → бот» объект `link` не сохраняет идентификаторы промежуточного канального поста и канала. При этом исходное содержимое доступно через `link.message`. Поэтому бот не может надёжно получить дату именно этой промежуточной публикации, хотя MAX API возвращает timestamp самого поста канала.

Это вывод о наблюдавшемся сплющенном пути «человек → канал → бот». Это не означает, что MAX API нигде не возвращает дату канального поста: API возвращает её при доступе к посту по его ID или при чтении доступной истории канала. В этой пересылке надёжной связи с таким ID нет.

Автоматически подбирать запись истории по тексту, `seq`, вложениям, ID исходного сообщения или их комбинации нельзя считать достоверным решением. Один исходник может быть опубликован повторно; аналогичный материал может прийти напрямую или из другого канала. Окно истории также ограничено запрошенным диапазоном. Совпадение кандидата не доказывает происхождение пересылки. Автоматическая корректировка даты записи не выполнялась.

## Основание

Ведущий выполнил GET-only запросы к MAX API с production bot token, который оставался на сервере, и использовал только read-only доступ к базе. Записанные диагностические скрипты находятся вне Git: `.diagnostic/channel-post-date-readonly.mjs` и `.diagnostic/channel-post-date-chain-readonly.mjs`. Здесь они не запускались. Никаких production-записей не меняли.

В наблюдении альбома внешняя пересылка содержала тип, время получения ботом, отправителя, `link.chat_id` и вложенный `link.message` с `mid`, `seq`, текстом и шестью изображениями. Timestamp исходной публикации отсутствовал. `link.chat_id` совпадал с исходным чатом в обеих проверенных цепочках и отличался от привязанного семейного канала; его тип не выводится из ответа. Запрос `GET /messages?message_ids=…` вернул HTTP 200 с пустым массивом, `GET /messages/{messageId}` — 404, `GET /chats/{chatId}` — 404.

В отдельно разрешённой выборке истории канала за диагностическое окно 5–9 октября был найден альбомный пост с timestamp `2026-10-06T14:52:13.954Z`. Его `link.message` совпадал с пересланным исходником по `mid`, `seq`, тексту и типам/ID вложений, но `body.mid` самого поста отличался от `link.message.mid`. Точный ID канального поста успешно возвращал этот объект. Внешняя пересылка не содержала ID этого поста или промежуточного канала.

Видео прошло такую же цепочку: внешняя пересылка имела время получения, но не дату исходной публикации и не ссылку на промежуточный пост/канал. Канальный пост с тем же вложенным исходным сообщением имел timestamp `2026-10-08T14:03:41.706Z` и был доступен по точному ID.

Контрольная выборка включала 10 обычных пересылок **из канала боту**, для которых `mid` канального поста удавалось получить и использовать timestamp. Среди них были подписи, видео, а также смешанные вложения «2 изображения + видео + 4 изображения». Это показывает, что такой прямой путь сохраняет пригодную связь, тогда как проверенный сплющенный путь «человек → канал → бот» — нет.

## Текущая обработка даты в коде

`backend/src/modules/max/transport/update-mapping.ts` (строки 29–31, 227–233) берёт внешний `update.timestamp` как начальный `event.occurredAt` и сохраняет `link.message.timestamp` отдельно, если оно присутствует. `backend/src/modules/max/infrastructure/max-api.ts` (строки 202–210) при точном GET сохраняет timestamp проверенного сообщения и timestamp его `link` раздельно. В `backend/src/modules/max/infrastructure/process-task.ts` (строки 256–266) успешная проверка исходного поста заменяет `event.occurredAt` на `verifiedForward.timestamp`; если пост не удалось разрешить и обработка перешла на envelope fallback, выбирается `validForwardTimestamp(outer.forwardedFrom?.timestamp) ?? inbox.receivedAt`. Затем (строки 329–335) `event.occurredAt` записывается как в `occurredAt`, так и в `sourcePublishedAt`.

Следовательно, fallback на timestamp `link` — действующее поведение, но эта дата относится к связанному исходному сообщению и сама по себе не устанавливает дату промежуточной канальной публикации. Точные GET-only наблюдения выше показывают, что envelope не позволяет запросить найденный пост канала по его ID.

Публичная документация подтверждает форму API: объект `Message` имеет `timestamp` и необязательный `link` ([описание `Message`](https://dev.max.ru/docs-api/objects/Message)); `GET /messages` читает посты канала по `chat_id` при наличии прав администратора либо конкретные объекты по `message_ids` ([получение сообщений/постов](https://dev.max.ru/docs-api/methods/GET/messages)); `GET /messages/{messageId}` принимает ID сообщения/поста (`mid`) и возвращает timestamp ([получение по ID](https://dev.max.ru/docs-api/methods/GET/messages/-messageId-)). Документация не устанавливает, что ID промежуточного канального поста обязательно присутствует в пересланном `link`.

## Пользовательский обходной путь

У записи ленты предусмотрено действие «Редактировать» с подписью «Изменить подпись или дату»; переход выполняется по capability `edit` записи (`webapp/src/features/feed/FeedPage.tsx`, строки 418–421, 729–733). `MemoryEditor` открывает форму редактирования и сохраняет `occurredAt` (`webapp/src/features/composer/MemoryEditor.tsx`, строки 17–33). Поле даты отображается как «Дата воспоминания» в общем редакторе (`webapp/src/features/composer/ComposerForm.tsx`, строка 108). Пользователь с ролью полного доступа может вручную поставить известную дату; просмотрщик это действие не получает.

`occurredAt` — редактируемая дата воспоминания. Она не подтверждает время публикации канального поста. Текущий fallback берёт timestamp связанного сообщения, если он есть, иначе — `inbox.receivedAt`; timestamp автора вложенного сообщения не доказывает дату промежуточной канальной публикации.

## Возможное отдельное направление

Для будущего автоматического исправления источнику потребуется явная проверяемая ссылка на конкретный пост канала: например, введённый пользователем ID/ссылка, после чего сервер сможет проверить доступ к посту и его timestamp. Такой интерфейс и контракт здесь не реализованы и не утверждены; это отдельный вопрос продукта и архитектуры. Автоматическая эвристика по похожему содержимому не предлагается как безопасная замена.
