# DIAG-PWA-WHITE-SCREEN

Status IN_PROGRESS. Owner approved durable local diagnostics and default deployment after green checks. Lead GPT-6; task branch `fix/pwa-crash-diagnostics`, worktree `.worktrees/pwa-crash-diagnostics`; base `ac3309886c0fbafc94497062c68bff8ab1458092`.

Outcome: after an installed iPhone PWA white bootstrap/restart, the owner can copy a bounded, privacy-safe technical report from the startup error screen or Settings → About memoLy. This gathers evidence; it is not an assertion that the underlying crash is fixed or caused by memory pressure.

Approved implementation:
1. An early dependency-free diagnostic bootstrap runs inline before the current startup handler and app modules. Keep its source separately testable; Vite can inject the plain JS source with a narrow HTML transform. No additional startup network request, dependency, backend endpoint, automatic report submission, or production data changes.
2. Persist only current plus previous run, with at most 24 coarse event records per run and a hard serialized size cap (target ≤8KiB). Fixed categories, timestamps, phase, visibility/navigation category, safe build fingerprint (public hashed app bundle basename), and clamped numeric media resource counts only. No user/family/memory IDs, names/text, media URLs, raw exception messages/stacks, user agent, tokens, or arbitrary event payloads. Reconstruct and allowlist data read from storage; do not echo tampered arbitrary JSON. Storage and clipboard failures must never break app startup.
3. New boot preserves the preceding run before starting a fresh record. Lifecycle endings are descriptive only: interruption/hidden/pagehide never proves a WebKit kill or out-of-memory. Avoid false crash alarms or automatic retries. Catch post-mount uncaught error categories as well as existing pre-mount errors; capture React boundary failures explicitly. Existing retry remains manual.
4. Coarse feed/media activity is throttled and bounded; no storage write/DOM scan on every scroll event. Capture app-entry/module-ready/mounted, scroll/media load/error/play/pause, and carousel selection with only kind/phase, plus sampled counts (loaded image/video/audio/blob resources). Avoid monkey-patching fetch, URL ownership, media source/loading, or lifecycle behavior.
5. Add “Скопировать отчёт об ошибке” to static bootstrap failure and React error boundary. In Settings → About memoLy add a shared-style copy action. Clipboard rejection falls back to a selectable read-only report for manual copy on iPhone; report remains available after next boot. User explicitly chooses when to share it. No newly generated icons or navigation changes.

Allowed paths: `webapp/index.html`, `webapp/vite.config.ts` (lead-approved HTML transform only), new `webapp/src/platform/diagnostics/**`, `webapp/src/main.tsx`, `webapp/src/features/app/StartupBoundary.tsx`, `webapp/src/features/memoly-ui/SettingsSheet.tsx`, a small diagnostics UI component if needed, targeted `FeedPage.tsx` event call only if DOM listeners cannot identify carousel selection, focused `webapp/tests` behavior tests, this report and ignored artifacts. Forbidden: backend/storage/contracts/schema/deploy/package/lockfile/other UI changes. One worker owns all product paths; lead owns integration and review of the shared Vite change.

Tests: meaningful small behavior tests using the actual bootstrap source to verify run recovery, event/size/write-rate bounds, sanitation of hostile stored/input data, storage exceptions, lifecycle/error categories. One focused actual browser scenario verifies real built inline script order, module failure + static copy fallback, restart/report retention, and Settings/About access using synthetic data; no viewport/theme matrix. Run narrow checks after the concrete implementation, one fresh independent review with one bounded fix pass, then a single `bun run verify:local` on exact published product source. Existing cached Linux runtime/Chromium/Docker verification and guarded manual Selectel release are reused.

STOP: if new backend/schema/dependency or private data collection is needed, ask lead for ruling. If device termination remains indistinguishable, report that limitation rather than adding speculative crash classification. No unrequested resource/performance fix in this diagnostics task.
