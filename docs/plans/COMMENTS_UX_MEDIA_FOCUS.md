## Synchronization rulings

- Existing API returns descending `(createdAt, id)` cursor pages of 20 rows. Use this ordered position as the authoritative interval boundary, not count changes or id overlap alone. Fetch from latest until the fetched oldest position crosses the previous newest position (or end-of-history), then replace that interval atomically and retain only older cached rows. Keep real continuation cursors. A burst larger than one page must be bridged before display; never expose an unverified gap.
- Refresh only the latest window on ordinary ticks. A currently read older window may also be reconciled using its existing input cursor, and on scroll demand; replace the returned ordered interval, including absent/deleted rows. Keep latest and older ranges separate when they do not connect. Retain stable id/version ordering and never resurrect deleted items from overlapping old pages.
- Serialize initial/list/pagination/window reads. Before a mutation starts, abort reads, cancel query ownership, advance a revision and block background reads until the server result has been applied. Late responses must fail both scope and revision checks before cache writes. Coalesce background triggers through one scheduler; mutation completion may request one latest-window refresh but must not invalidate/reload every loaded page or feed summaries.
- It is acceptable to retain the TanStack infinite-data shape while replacing its default all-page refetch with an explicit controller. Do not change backend contracts. Retry-After metadata may be exposed by the existing HTTP error class and must apply as a minimum retry deadline even to focus/reconnect triggers.
- Conflict recovery must refresh the window containing the edited/deleted target, even when it is outside the latest page; do not refresh only latest and retry a stale expectedVersion forever. Preserve the user's edit body while replacing its expected version from that authoritative target window. The same serialization/revision rule applies to demand loads and mutation conflict recovery.

## Avatar ownership ruling

Extend the existing private-image hook only for eligible immutable member-avatar paths. Share resource/in-flight work across feed, direct member avatars and comments in the same account identity generation, family generation and image version. Membership epoch changes already revoke the family's private-cache scope in App; verify that path rather than modifying auth. Keep crop in presentation. Ordinary photos/viewer URL ownership stays on its existing path.

Use reference-counted leases with finite idle TTL, LRU entry/byte budgets and per-image size bounds. Live consumers protect their URLs from ordinary eviction. Privacy disposal (identity/user/family/all, including switching the active family) aborts requests, revokes resources and notifies consumers synchronously; late cache/decode/network results cannot publish. A small generic invalidation subscription in existing private-cache is permitted to ensure lifecycle disposal without importing feature code there. Persistent comments/drafts remain forbidden. A new avatar id gets a new path; crop-only changes reuse bytes with fresh crop presentation.

The existing member-avatar route serves supported JPEG/PNG/WebP bytes unchanged (up to the existing 5 MiB upload bound); only HEIC normalization is performed. Do not assume all avatars are tiny derivatives or introduce a 2 MiB display rejection. Budget exhaustion may stop idle retention/admission but must not hide a valid avatar or revoke another consumer's live URL. Distinguish bounded retained-cache bytes from resources currently leased by visible components, and verify eviction/resource disposal explicitly. Do not introduce a new avatar resize engine in this task.
