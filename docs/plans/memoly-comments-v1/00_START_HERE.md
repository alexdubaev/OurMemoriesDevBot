# memoLy — комментарии: пакет заданий для агента

Дата подготовки: 20 октября 2026 года.
Статус: ТЗ подготовлено для передачи; реализация, миграции и выкладка по этому пакету не выполнялись.

## Результат

Добавить закрытые текстовые комментарии к каждой опубликованной записи memoLy. Использовать действующие React-компоненты, API, PostgreSQL, авторизацию и семейные проверки. Не устанавливать Remark42, react-comments-section, их forks или новый движок обсуждений.

Это одна продуктовая функция, разбитая на четыре последовательно назначаемых задания:

| Этап | Файл | Проверяемый результат |
|---|---|---|
| COM-1 | `COM-1_CREATE_READ.md` | Данные, создание, чтение и пакетные счётчики; безопасный повтор отправки |
| COM-2 | `COM-2_EDIT_DELETE.md` | Изменение и удаление, серверные права, конфликты и отзыв доступа |
| COM-3 | `COM-3_UI_INTEGRATION.md` | Готовые комментарии в ленте v4 через настоящий API |
| COM-4 | `COM-4_ACCEPTANCE_RELEASE.md` | Сквозная проверка, готовность к выпуску и отдельно разрешённая выкладка |

COM-1 → COM-2 → COM-3 → COM-4. Не выполнять все четыре по одному назначению. Внутри назначенного этапа работать автономно, без согласования каждого файла и каждого теста.

## Как читать

Сначала `AGENTS.md`, `.agents/skills/teamlead-development/SKILL.md` и обязательные стартовые документы репозитория. Затем этот файл, `01_COMMON_REQUIREMENTS.md`, только назначенное задание и handoff предыдущего этапа. Ссылки на проверенные исходники — в `SOURCES_AND_BASELINE.md`.

Этот пакет — отдельное расширение продукта по прямому запросу владельца. Старое «комментарии не входят в MVP» больше не запрещает именно эту функцию. Оно не разрешает добавлять уведомления, другие мессенджеры, платежи, независимую авторизацию, новые видеохранилища или нативные приложения: обсуждения этих идей не являются их реализационным заданием.

Правила первой версии, в том числе разрешение Viewer комментировать и право Owner удалять чужие комментарии, — явно предложенные правила ЭТОГО ТЗ. Не выдавать их за уже существующее поведение. Передача задания на реализацию означает применение этих правил; при отличающемся решении владельца сначала обновить общий документ один раз.

## Ветки и зависимости: без скрытого merge UI v4

По умолчанию соблюдать действующий процесс: одна task-ветка/один worktree/один PR на назначенную задачу, ветка от принятого актуального main; без stacked PR, копирования между worktrees и изменения чужой ветки.

- COM-1 серверный и может стартовать от актуального main, не ожидая визуальной приёмки v4. Сначала подтвердить, что серверные точки интеграции существуют в этом baseline.
- COM-2 начинается, когда результат COM-1 включён в принятую базу. Наличие одного отчёта или неслитого PR не равно наличию зависимости.
- COM-3 требует принятого backend COM-1/2 и принятой реализации v4. Пока #185 Draft, не сливать его ради комментариев и не подменять его старым UI из main. При отсутствии подходящей базы вернуть один конкретный блокер `WAITING_FOR_APPROVED_BASE`, не запускать обходную архитектуру.
- Продолжение в одной выделенной feature-ветке возможно только при отдельном явно указанном владельцем исключении. Новый агент сначала получает handoff, проверяет, что предыдущий закончил, и не переписывает историю.

Назначение этапа не является разрешением сливать чужие PR. Этот пакет не объявляет UI v4 принятым.

## Границы полномочий пакета

Сейчас подготовлены документы, а не команда этому чату на реализацию.

При назначении COM-1/2/3: локальная реализация, тесты, review, небольшие коммиты, обычный push своей ветки и draft PR в подтверждённый origin — по правилам и фактическому разрешению владельца. Промежуточные production-деплои в этом пакете НЕ нужны. Merge — по действующим правилам и разрешениям, не подразумевается одной только готовностью кода.

COM-4 по умолчанию заканчивается `READY_FOR_OWNER_PREVIEW`. Production-операции разрешены только если в назначении COM-4 явно разрешены API/frontend rollout и новая additive migration. Разрешение на прошлые frontend-only правки таким разрешением не считать.

При отдельном разрешении на выкладку использовать существующий `app.memoly.ru`, а не требовать нового домена, сервера или бота. Сохранить rollback. Финальный merge #185 по-прежнему требует явной приёмки владельца.

## Проверки без бесконечных циклов

Тесты создаются вместе с кодом COM-1/2/3, а не откладываются на COM-4. Использовать существующий risk classifier: данные, контракты и ACL — соответствующий полный профиль; не снижать его искусственно. Полный pre-release gate выполняется на точном итоговом source, а не после каждого CSS-движения.

Независимое read-only review — по AGENTS.md на конкретном diff. Обычная граница: одно review → ограниченное исправление подтверждённых замечаний → одна узкая повторная проверка. На следующем этапе не повторять закрытый аудит неизменённого кода. Нет доступного независимого reviewer — честно указать, не выдавать self-review за независимое.

Только task-owned синтетическая БД `*_test`, отдельные порты/Compose/storage, проверенные `TEST_DATABASE_URL` и `DATABASE_URL`. Не запускать тесты против production и чужих проектов. Не создавать paid infrastructure. Не публиковать тексты, фотографии, токены и cookies реальных семей.
