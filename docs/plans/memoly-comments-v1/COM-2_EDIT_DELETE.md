# COM-2 — изменение, удаление и конкурентный доступ

**Цель:** безопасное управление уже сохранёнными комментариями, без потери чужих изменений и без доступа после отзыва участия.
**Архитектура:** дополнение сервиса и repository COM-1, без нового движка, очереди или процесса.
**Стек:** прежний backend и готовые contracts COM-1.
**Спецификация:** `00_START_HERE.md` + `01_COMMON_REQUIREMENTS.md`.
**Зависимость:** COM-1 принят и присутствует в разрешённом baseline; его handoff прочитан.
**Не входит:** UI, уведомления, изменения авторизации, синхронизация с MAX, production-деплой.

## Файлы

Изменить только comment-service/comment-ports/prisma-comment-repository/comment-routes/comment-errors и новые contracts при подтверждённом локальном дефекте. Новые поля БД обычно не нужны: version/deletedAt/create marker уже предусмотрены COM-1.

Создать:
- `backend/src/modules/memories/comments-mutations.integration.test.ts`;
- `backend/src/modules/memories/comments-races.integration.test.ts`.

Допустимы минимальные изменения существующего удаления Memory/семьи/аккаунта только если иначе новые данные действительно остаются вне действующей процедуры. Не превращать это в аудит всей privacy-инфраструктуры. Миграцию COM-1 не редактировать после применения; необходимость новой миграции отдельно объяснить.

## Публичные результаты

Добавить `update(scope, memoryId, commentId, input)` и `delete(scope, memoryId, commentId, expectedVersion)`, подключить PATCH/DELETE по общему контракту.

Вернуть реальные capabilities: edit — только автору; delete — автору или Owner этой семьи. Full не равен Owner. Во всех случаях требуется актуальное членство и доступная опубликованная Memory. Удаление комментария не удаляет публикацию и не меняет её системного автора.

## Порядок

- [ ] Проверить контракт COM-1 и реальные права; воспроизвести его зелёный baseline только узкой необходимой проверкой.
- [ ] Написать tests own/foreign edit/delete, expectedVersion, двойное удаление и replay создания после изменения/удаления; получить осмысленный red.
- [ ] Реализовать атомарное сравнение версии. Успешное изменение увеличивает version, сохраняет createdAt и обновляет updatedAt серверным временем. Conflict не перетирает актуальный текст.
- [ ] Реализовать удаление: исключить из списка и count, очистить body, оставить необходимый tombstone и initial fingerprint. Без корзины/восстановления в v1. Не возвращать удалённый текст через replay, exports либо новый list endpoint.
- [ ] Проверить на барьерах/управляемых транзакциях гонки с revoke, удалением Memory, двумя edits и edit/delete. Не заменять race tests случайными sleep.
- [ ] Проверить участие новой таблицы в существующем физическом purge Memory/семьи/аккаунта и сохранность уже работающего membership revoke. Соблюсти существующую семантику, не придумать новый глобальный retention.
- [ ] Целевые проверки → применимый risk gate → одно bounded review и closure. Зафиксировать handoff без запуска UI-этапа.

## Обязательная матрица

1. Все три роли изменяют и удаляют своё. Только Owner удаляет чужое, никто не редактирует чужое. Участник двух семей не переносит права Owner из одной в другую.
2. Две правки из version=1: одна подтверждается, вторая получает conflict; итог ровно один, без «последний молча победил».
3. Edit/delete race: deleted body не возникает заново; счётчик не отрицательный и не уменьшается дважды.
4. Повтор DELETE безопасен только после повторной авторизации/проверки права; чужой и исключённый не получают даже данные ответа.
5. Воспроизведение старого POST после edit возвращает актуальную допустимую запись, не восстанавливает первоначальный текст. После delete не создаёт дубль и не возвращает удалённый body. Отсутствие временной idempotency записи не ломает это поведение.
6. Удаление Memory/семьи закрывает list/count/write. После завершившегося отзыва членства новых успешных действий от пользователя нет; транзакции имеют определённый порядок, не TOCTOU между отдельной проверкой и записью.
7. Пользовательский authorId и дата не изменяются. Индекс/сортировка ленты, реакции, MAX source identity и backups не затронуты.
8. Snapshot/idempotency logs/cache не служат обходом удаления. Не публиковать тексты в обычные application logs.
9. После физического purge не остаются orphan comment rows; новые FK не останавливают штатное удаление семьи.

## Готовность

Реальный локальный API обслуживает полный жизненный цикл комментария; права, конфликт и удаление подтверждены. Зафиксированы DTO/codes/capabilities, которые потребляет COM-3. Нет фронтенда и production acceptance — не объявлять их готовыми.

Передать отдельный handoff: SHA, endpoint примеры на синтетических данных, список тестов и кодов ошибок, влияние на миграции/удаление, разрешённая следующая база. COM-3 не начинать до отдельного назначения и доступности принятого UI v4.
