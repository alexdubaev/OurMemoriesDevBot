# COM-4 — сквозная приёмка и контролируемый выпуск

**Цель:** подтвердить взаимодействие выполненных этапов и подготовить безопасный выпуск, не повторяя общие расследования проекта.
**Архитектура:** существующий API/frontend/PostgreSQL, существующий guarded deployment; не новая инфраструктура.
**Основание:** `00_START_HERE.md`, `01_COMMON_REQUIREMENTS.md`, handoff COM-1/2/3 и действующий deployment runbook.
**Зависимости:** точный интегрированный source с COM-1/2/3 и принятым v4. Нельзя принять это требование за разрешение сливать #185.
**По умолчанию:** тесты и release readiness, без production action. Выкладка только при отдельно указанном разрешении API/frontend/additive migration в назначении этого этапа.

## Что не надо делать

Не добавлять уведомления, ответы, новый realtime или UX. Не заказывать новый сервер/домен/бота. Не повторять аудит всего MAX, private media, авторизации или ролей, если их код не менялся. Не запускать один и тот же whole-change review повторно ради статуса.

Не заявлять, что комментарии готовы только потому, что UI работает с mock API. Не выполнять destructive journeys/синтетические записи против production. Не называть проверку rollback в моках реально выполненным обратным переключением.

## Порядок

- [ ] Проверить включение всех результатов и отсутствие чужих незакоммиченных изменений. Сверить migration set и версии contracts. Записать точный release candidate SHA/tree и baseline API/frontend/schema.
- [ ] Провести одну сквозную сессию на реальном локальном API и отдельном PostgreSQL `*_test` с синтетическими MAX/Web/PWA identities. Обычный вход, две семьи, Owner/Full/Viewer, реальные запросы комментариев.
- [ ] Закрыть только подтверждённые интеграционные дефекты ограниченным diff. После изменения повторить соответствующий тест; полное повторное независимое review старого кода не запускать. Новые security/migration решения вернуть интегратору.
- [ ] Запустить действующий FULL на точном окончательном source. Результат привязать к SHA; прежние FULL UI-v4/COM-1 не заменяют новый pre-release gate.
- [ ] Подготовить совместимость и rollback по разделу ниже. Без разрешения deployment завершить `READY_FOR_OWNER_PREVIEW` и остановиться.
- [ ] Только при наличии разрешения выполнить guarded rollout на существующем app.memoly.ru и ограниченный smoke; записать реальные активные SHA, images/digests, applied migrations. Ожидать физическую приёмку владельца без автоматического финального merge.

## Сквозные сценарии

1. Owner, Full, Viewer читают/пишут; Viewer не публикует медиа; имена/аватары/crop правильные под каналом и ручным постом.
2. Другой аккаунт/семья/отозванный участник не получает список, batch count и операции даже по известным ID.
3. Потеря ответа после committed POST и повтор дают один comment. Редактирование из двух сессий вызывает conflict, удаление не воскресает от retry.
4. Удаление Memory/семьи и смена epoch не оставляют доступного обсуждения, приватного кэша и зависшего черновика.
5. После открытия/закрытия/редактирования комментариев остаются рабочими реакции/long-press, swiper, fullscreen, voice, video release, MAX Back, позиция ленты.
6. Проверенная базовая нагрузка: 50 карточек, несколько страниц одного обсуждения, два одновременных пользователя; нет N+1, бесконечной подгрузки/роста timers и повторных listeners. Не запускать нагрузочный тест production.
7. Проверить старый frontend с новым backend/schema; новый frontend корректно переживает недоступность новых endpoints при rollback, не ломая ленту. Ошибку private-запроса нельзя объявлять доказательством отсутствия поддержки комментариев.

Для e2e использовать существующий runner/синтетический auth harness; при необходимости добавить один `webapp/e2e/comments-api.spec.ts` с task-owned конфигурацией. Дополнительные файлы — только там, где существующие tests не подтверждают реальный стык.

## Миграция и rollout

Прочитать `docs/DEPLOYMENT.md`, `deploy/selectel/README.md` и свежий отчёт активного preview. Подтвердить реальную рабочую конфигурацию сервера; значения из этого пакета исторические.

- Миграция расширяющая: новая таблица/индексы/FK; старые таблицы не переименовывать и данные не переписывать. Совместимость со старым runtime подтверждается на test DB.
- Сохранить backup в принятом порядке, действующий manifest, baseline образы и возможность code rollback. Штатные main-only guards не отключать.
- Изменение НЕ frontend-only: кандидат API обязан содержать проверенную schema/сгенерированный client и routes. Старый оператор только для CSS/static нельзя использовать как универсальный оператор этой поставки.
- Порядок при подтверждённой совместимости: additive migration → API → frontend; один оператор/lock. Не запускать миграцию каждым контейнером.
- Worker/scheduler, webhook и binding MAX не менять без фактической необходимости. Если принятому runbook требуется обновление связанных контейнеров, отразить impact, а не обходить guard.
- Если feature-preview путь не поддерживает такую миграцию/сборку, указать конкретный блокер и безопасный путь по разрешениям. Не собирать неподтверждённый overlay «по аналогии» и не требовать автоматически новую платформу.

## Rollback

Откат кода не удаляет новые комментарии. Сначала убрать/откатить frontend-функцию, затем при необходимости вернуть совместимый API. Новую additive таблицу оставить: down migration с DROP и восстановление старого backup могут уничтожить реальные новые записи и не разрешены этим заданием.

Не использовать команды из старого nav/fullscreen/longpress deployment вслепую. Нужен rollback именно текущего candidate/baseline и доказательство совместимости схемы. Если old API несовместим с расширенной схемой, это блокер до активации, а не повод экспериментировать в production.

## Smoke и владелец

После разрешённой выкладки: public health/static/build markers, доступность API, анонимный отказ на private comment routes, корректные server error codes без body утечек. Никаких искусственных owner-сессий и массовых тестовых комментариев в реальных семьях. Авторизованные write-сценарии в production — только действия владельца либо отдельно разрешённая им контролируемая проверка.

Ручная проверка iPhone/MAX для владельца:
1. Открыть комментарии под фото и видео, написать, исправить и удалить своё сообщение.
2. Повторить от Viewer; доступ к загрузке медиа не появился.
3. Проверить клавиатуру, отправку, закрытие/Back, положение ленты и прежнюю карусель.
4. При временной потере сети текст остаётся, retry не дублирует запись.
5. Проверить личное имя/аватар под постом канала, а не атрибуцию каналу.

Статусы различать: `READY_FOR_OWNER_PREVIEW`, `DEPLOYED_OWNER_SMOKE_REQUIRED`, `OWNER_ACCEPTED`. Не ставить последний без фактического сообщения владельца. Финальный merge/обычный выпуск — только по действующим разрешениям; этот этап не объявляет #185 принятым автоматически.
