# Общая спецификация комментариев memoLy v1

## 1. Объём и права

Комментарии относятся к опубликованной записи memoLy независимо от её типа: `note`, `photo`, `video`, `voice`, `media`, ручная или импортированная. Старые записи не требуют backfill: отсутствие строк комментариев означает нулевой счётчик.

Первая версия: плоское обсуждение, обычный текст и Unicode-эмодзи, создание, изменение и удаление. Без вложенных ответов, Markdown/HTML-редактора, вложений, отдельных реакций на комментарии, уведомлений, unread-комментариев, WebSocket, фонового polling, синхронизации с MAX и публичных страниц.

| Действие | Owner | Full, не Owner | Viewer |
|---|---|---|---|
| Читать и добавлять комментарии в своей семье | Да | Да | Да |
| Изменять свой комментарий | Да | Да | Да |
| Изменять чужой комментарий | Нет | Нет | Нет |
| Удалять свой комментарий | Да | Да | Да |
| Удалять чужой комментарий | Да | Нет | Нет |
| Публиковать фото/видео | Только прежние права, без изменений | Только прежние права, без изменений | Новых прав нет |

Все разрешения проверяются сервером. Owner определяется существующим владением семьёй, а не значением `full`. Автор публикации не получает автоматически права удалить чужой комментарий, если он не Owner.

После исключения участника или потери сессии недоступны чтение, счётчики и все операции. Повторное присоединение определяется действующей моделью membership/epoch, без обхода существующей авторизации. Исторические комментарии исключённого человека остаются у семьи до удаления, но его недоступные личные медиа не выдаются; применять действующие правила имён и fallback. Отзыв участия и удаление аккаунта не смешивать. Новая таблица должна участвовать в существующих процедурах удаления данных, не создавать неучтённую вечную копию.

## 2. Текст, автор и даты

Тело: 1–2 000 Unicode code points после единой нормализации CRLF → LF и trim внешних пробелов. Внутренние переводы строк сохраняются. Пустой/пробельный текст, NUL и превышение лимита отклоняются. Клиент и сервер используют общий контракт. HTML выводится как текст, а не исполняется; никаких `dangerouslySetInnerHTML`, авто-embed и внешних link previews.

Автор берётся из серверной сессии, не из тела запроса. Имя в UI: семейное имя → имя профиля → «Участник семьи» по доступным данным. Аватар — личный с существующим crop/private loader. Название/аватар MAX-канала принадлежат публикации, не её комментариям.

`createdAt`, `updatedAt` назначает сервер; в UI использовать семейный timezone и существующие форматтеры. После изменения показать «изменено». Не наследовать дату старого MAX-поста в новый комментарий.

## 3. Данные и совместимость

Предлагаемая модель `MemoryComment` в существующем PostgreSQL:
`id`, `familyId`, `memoryId`, `authorId`, `body`, `createdAt`, `updatedAt`, `version`, `deletedAt`, `createRequestId`, `initialPayloadHash`.

Последние два поля — минимальная долговременная защита от повторного создания; не выдавать их в публичном DTO. Уникальность `(familyId, authorId, createRequestId)` и fingerprint исходного `memoryId + normalizedBody` должны исключать дубли и повторное использование ключа для другой публикации/текста. Применять существующий idempotency executor/секрет/паттерны, где они подходят; не строить вторую глобальную подсистему идемпотентности.

Обязательная связь `(memoryId, familyId)` → `Memory(id, familyId)` на уровне БД. Связь автора с семейным участием — по существующему паттерну family membership и согласованной политике удаления. Индекс чтения по семье, записи и `(createdAt, id)`, с учётом `deletedAt`. Проверить, что новые FK не блокируют существующий purge семьи/учётной записи.

В COM-1 создаётся одна additive migration. Уже применённые миграции не редактировать; не менять существующие Memory-поля ради комментариев. Комментарий не обновляет `Memory.version`, `occurredAt`, `updatedAt`, publication ordinal, импортную identity, unread или порядок ленты.

Существующий `MemoryDto` строгий. В этой версии НЕ добавлять в него `commentsCount`/capabilities. Счётчики передаются отдельным пакетным endpoint. Это исключает необходимость менять старые ответы create/update/импортные snapshots ради новой функции.

## 4. Новый контракт API

Это проектируемые endpoints, не утверждение об их наличии в текущем коде. Общий префикс `/api/v1`. Контракты — `packages/contracts/src/comments.ts`, экспорт через действующий index.

### DTO

```ts
type CommentDto = {
  id: string;
  familyId: string;
  memoryId: string;
  author: {
    id: string;
    name: string;
    avatarPath: string | null;
    avatarCrop: AvatarCrop | null;
  };
  body: string;
  createdAt: string;
  updatedAt: string;
  version: number;
  capabilities: { edit: boolean; delete: boolean };
};
type CommentSummary = {
  memoryId: string;
  count: number;
  capabilities: { read: boolean; create: boolean };
};
```

UUID, avatar path/crop и datetime валидировать существующими схемами. Внешние provider URL, cookies и внутренние idempotency поля не выдавать.

### Операции

| Операция | Вход | Ответ |
|---|---|---|
| GET `/families/{familyId}/memories/{memoryId}/comments` | `limit=20`, максимум 50; optional `cursor` до 2 048 символов | `{items: CommentDto[], nextCursor: string|null, summary: CommentSummary}` |
| POST по тому же пути | `{body}` + обязательный `Idempotency-Key: UUID` | первый запрос 201, replay 200: `{comment: CommentDto, summary: CommentSummary}` |
| PATCH `.../comments/{commentId}` | `{body, expectedVersion}` | 200: `{comment: CommentDto, summary: CommentSummary}` |
| DELETE `.../comments/{commentId}` | существующий паттерн `If-Match` с версией | 200: `{deletedId: string, summary: CommentSummary}` |
| POST `/families/{familyId}/memories/comment-summaries` | `{memoryIds: UUID[]}`: 1–50, без дублей | `{items: CommentSummary[]}` |

Пакетный POST только читает. Идемпотентность записи для него не нужна. Маршрут разместить так, чтобы `comment-summaries` не перехватывался динамическим `memoryId`. Отсутствующие/недоступные записи пропускаются; их отсутствие НЕ превращать в count=0. При отсутствии участия в самой семье отклонить весь запрос.

Список — keyset pagination `createdAt DESC, id DESC`; `nextCursor` ведёт к более старым комментариям. UI разворачивает загруженные записи в хронологическую переписку и загружает старые сверху. Cursor связан с семьёй и записью и проверяется сервером; не пользоваться offset. Удаление строки не должно делать cursor зависимым от наличия самой строки. Полный мгновенный snapshot длинного обсуждения не требуется. Точность createdAt в cursor должна совпадать с точностью хранения/сравнения в БД: не обрезать микросекунды незаметно для keyset; допустимо сразу выбрать для новой таблицы миллисекундную точность и проверить пограничные даты.

### Ошибки и защита

Использовать существующий envelope ошибок. Семантика: 400 валидация; 401 нет действующей сессии; 404 чужая/недоступная семья, запись или комментарий; 403 недопустимая операция над доступным чужим комментарием; 409 `VERSION_CONFLICT` / `IDEMPOTENCY_CONFLICT` / уже удалённая цель replay; 429 существующий rate limiter. Точные имена кодов согласовать с кодовой базой в COM-1 и зафиксировать в handoff; семантику не менять.

Отклонять неизвестные поля запросов, включая попытки передать authorId/роль/время. Применить существующий origin/CSRF/auth/rate-limit механизм, а не обходить его. Для новых write routes установить явный лимит размера JSON не более 16 КиБ и использовать штатный rate limiter; не добавлять Redis или внешний антиспам ради этого этапа. Все ответы комментариев, включая счётчики и ошибки с данными, `Cache-Control: private, no-store`. Не включать тексты в аналитику и обычные request-body логи.

## 5. Надёжность записи

POST: один пользовательский submit — один UUID ключ и неизменяемый payload попытки. Двойное нажатие, конкурентные повторы и «сервер сохранил, но ответ потерялся» дают одну запись. После очистки временных idempotency snapshots уникальный marker строки всё ещё препятствует дублю. Повтор с другим payload под тем же ключом — конфликт.

До replay заново проверять действующий доступ, состояние семьи/публикации и актуальное состояние комментария. Не возвращать сохранённый текст из старого snapshot после удаления/отзыва доступа. Повтор POST после редактирования не перезаписывает текст первоначальным; после удаления не восстанавливает строку.

PATCH: версия сравнивается атомарно. Два разных редактирования одной версии не перетирают друг друга. DELETE: удалённый текст не возвращается и не учитывается в счётчике; очистить body, оставить только необходимый tombstone/marker для защиты от replay. Повтор DELETE уже удалённого комментария от всё ещё уполномоченного актёра безопасен и возвращает актуальный summary; к живой строке применяется If-Match. Физический purge родительской записи/семьи удаляет связанные строки по правилам проекта.

Проверки доступа и изменения связать транзакцией/блокировками по существующему порядку захвата, чтобы отзыв membership и удаление Memory не оставляли окно записи. Не повышать всем уровень изоляции и не блокировать всю таблицу ради одной записи.

## 6. UI и жизненный цикл

Одна панель обсуждения для выбранной записи, не редактор под каждой карточкой. Под постом компактная кнопка «Комментарии» / «Комментарии · N» рядом с существующим блоком реакций, без внешней большой карточки. При нехватке ширины аккуратный перенос элементов, не уменьшение touch target ниже 44×44.

Панель переиспользует действующие диалоги, типографику, аватары, токены v4 и поддержку host/browser safe area. Поле с нативной клавиатурой и системными эмодзи. Не добавлять icon library; текстовая кнопка допустима, иконка — только из существующих разрешённых assets.

Неопределённый/ошибочный счётчик не рисовать как достоверный ноль. Не отправлять запрос на каждую карточку: запрашивать счётчики batch до 50 только для загруженных/нужных карточек, списки — только для открытого обсуждения. Никакого фонового опроса закрытых обсуждений. Обновление на открытие, возврат фокуса при открытой панели, после своих операций и по кнопке «Обновить»; live-мгновенность между устройствами не обещается.

Отправка для v1 — с подтверждением сервера, не ложный optimistic success. Пока запрос pending, повторная отправка отключена; текст очищается только после подтверждения. На ошибке текст остаётся. На сетевом timeout статус «Не удалось подтвердить отправку», повтор использует прежний ключ/payload. До разрешения неоднозначной попытки не выдавать отредактированный текст за тот же запрос: исходная попытка сохраняется отдельно от нового ввода либо редактирование её payload временно блокируется с объяснением.

PATCH/DELETE при конфликте обновляют данные и сохраняют черновик, не молча переписывают чужую новую версию. Удаление после явного подтверждения; отмена без побочных эффектов. Нет бесконечных автоматических retry для write.

Query keys и pending/draft scope включают account, family, membership epoch и memory. Реагировать на существующие события потери доступа, logout и смены семьи: закрыть панель, отменить запросы, очистить приватное состояние; поздний ответ не возвращает старые данные. Очистка должна охватывать новый namespace. Тексты не сохранять в localStorage/IndexedDB/service worker для v1.

Черновик существует только для открытого обсуждения. При обычном закрытии непустого черновика предложить «Продолжить писать» / «Закрыть без сохранения». Принудительное закрытие из-за logout/отзыва доступа не задерживать этим диалогом. Не накапливать Map черновиков всех просмотренных постов.

Клавиатура iPhone не перекрывает отправку; UI Back, MAX Back, Esc и закрытие через контролируемый overlay работают и возвращают к той же записи, позиции и индексу. Нельзя включать общий `touch-action: none` или глобальный preventDefault. Поле/панель комментариев не запускают long-press реакцию публикации. Сохранять выделение/копирование внутри поля, не возвращая выделение на reaction surface ленты.

Не менять Embla, PhotoSwipe, MixedMediaViewer, правила размеров, video lifecycle, освобождение objectURL, import/dedup и browser-link/F12. В первой версии новая точка входа только из ленты: не добавлять панели поверх fullscreen и не менять медиадвижки ради комментариев.
