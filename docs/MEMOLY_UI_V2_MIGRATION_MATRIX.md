## Блок 3: профиль участника, модель и права

Точки входа: `#family` → `#familyMember` (владелец), `#familyDad`/`#familyGrandma` (другие full), `#familyGrandpa` (viewer); photo picker, saved и remove dialog перечислены в inventory. Current user / other member в статике показаны примерами, а production определяет их из session и `userId`. Canonical не доказывает, что viewer видит все управляющие элементы или что full пользователь может менять чужой доступ: HTML не реализует authorization.

Права production: owner может изменить alias, роль и удалить **другого** участника; full может изменить alias любого не-владельца, включая себя; viewer не редактирует; target owner неизменяем через member PATCH. Это следует из `FamilyScreen` и `family-service`, а не из видимости контролов в статическом HTML. Нельзя расширить права по демо-радиокнопке. `expectedVersion` и conflict handling должны остаться.

### Граница реализации

**Frontend-only при существующей модели:** новая композиция owner/regular profile, account label, joinedAt, семейное имя у допустимых target, owner-only role selector, единый PATCH alias+role для actor owner и nonowner target, disabled/loading/error/conflict, навигация/back, success только по подтверждённому ответу, собственный React-dialog удаления вместо `window.confirm`. Сохранять текущие проверки прав и protected media; никакого hash JS.

**Требует отдельного решения владельца:** редактирование owner family name (backend сейчас запрещает), фото участника (account-global или family-local, кто меняет/удаляет, кому видно, формат/хранение, privacy), права full/viewer на себя и других, значение одновременного Save при фото+полях и частичном отказе, gender option в child editor, browser audio и multi-child состояния. Owner alias потребует contract/API/backend permission change; для owner `familyDisplayName` поле в DB уже есть, миграция может не потребоваться после проверки инвариантов. Семейное фото потребует DTO/API/upload purpose, backend authorization, storage/cleanup и, если оно family-local, новый DB field/table и migration. Account `UserAvatar` нельзя молча использовать для редактирования чужих аватаров или как семейную фотографию. Для изменения role/alias уже есть PATCH; DB миграция для этого не нужна. Во всех вариантах важны version conflict, ownership и privacy.

**Предлагаемый минимальный scope следующего шага:** Блок 3 на базе существующего member DTO/PATCH/DELETE: визуальная карточка, read-only account name/joinedAt, editable nonowner family name и owner-only access, атомарный для поддержанных полей Save, permission-aware controls, status/conflict и React remove dialog. Photo control и owner alias показать в плане как `UNCLEAR — OWNER DECISION REQUIRED`, без фиктивного сохранения. Общий bottom nav/back/buttons/cards/forms вынести в отдельный shared pass после решения владельца; локальная композиция Блока 3 может использовать текущие токены, не создавая новую theme system.

Ожидаемые paths для frontend scope: `webapp/src/features/memoly-ui/FamilyPresentation.tsx`, `webapp/src/features/family/FamilyScreen.tsx`, стили этих компонентов, при необходимости `webapp/src/features/family/api.ts` (только orchestration существующего PATCH). Общий pass отдельно: `webapp/src/components/BottomNavigation.tsx`, `webapp/src/features/memoly-ui/SettingsSheet.tsx`, theme tokens/shared controls. При утверждении нового avatar/owner поведения — `packages/contracts/src/families.ts`, `backend/src/modules/families/application/family-service.ts`, upload adapter/contracts и возможно `backend/prisma/schema.prisma` с миграцией. Конкретный allowlist и task ID следует назначить перед production edit.
