## Контекст

Воспоминание было жёстко привязано к одному ребёнку обязательным полем. Бриф требует «одного, нескольких или ни одного» ребёнка и отметки на отдельных фото и видео.

## Решение

Связь «воспоминание — ребёнок» хранится в отдельной таблице отметок. Строка без вложения означает «ребёнок на всём воспоминании», строка с вложением означает «ребёнок на этом фото или видео». Вложение в строке адресуется своим id без внешнего ключа, его существование проверяет сервис. Фильтр ребёнка — одна проверка «есть ли отметка любого уровня». Для одного ребёнка в одном воспоминании остаётся либо общая отметка, либо отметки на вложениях, не обе сразу.

## Почему

- Расширить поле ребёнка у воспоминания (второе поле или список). Один столбец не выражает много детей, а тем более отметку по конкретному фото. Вторая структура всё равно понадобилась бы.
- Две таблицы, одна на воспоминание и одна на вложение. Фильтр ребёнка превратился бы в объединение двух проверок, а правило «общая или по вложениям» пришлось бы держать между таблицами.
- Внешний ключ на вложение. Вложения приходят из трёх источников с тремя разными id (приватное хранилище, MAX-видео, Telegram-видео). Один ключ их не покрывает, а три nullable-ключа усложняют уникальность.

## Последствия

- База не защищает id вложения. Целостность держит сервис, и каждый путь записи обязан проходить через нормализацию. Обойти её значит получить отметку на несуществующем вложении.
- Когда вложение исчезает при доверенной перепубликации, отметки на нём подчищает код, а не база.
- Ребёнка с отметками нельзя удалить: ключ на ребёнка — Restrict.
- Миграция переносит каждое старое воспоминание в отметку на всё воспоминание. Откатывать этот перенос вручную нельзя без потери отметок, сделанных после выкладки.
- Фильтр по ребёнку держится на индексе таблицы отметок. Без него страница ребёнка будет сканировать ленту.
