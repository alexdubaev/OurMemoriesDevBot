## Navigation and state lifecycle

1. Complete existing auth/session restoration. Resolve explicit supported invite, memory, browser-link or confirmed publish destination first (`T-09.5.1.md` §6.1). An ordinary root/icon launch shows Hub even with one family. Resuming the existing view from background does not force Hub.
2. Hub renders server memberships. Selecting a `familyId` requests selected family detail and opens existing Feed; `setupStatus='needs_child'` for an owned family resumes existing child setup. Hub itself has no Add button because its publish target is ambiguous.
3. “Все семьи” is visible from Feed and the family root. Back first closes modal/detail/editor by existing rules, then moves to the prior page/Hub. Returning from Feed refreshes summaries/unread without replaying a consumed invite token. Logout clears selected family, per-account queries and pending seen state.
4. Invitation preview/accept remains scoped to its token family. On success refresh memberships and open that family or its existing setup destination. An unrelated membership never causes `OTHER_FAMILY` merely by existing; retain revoked/expired/used error semantics.
5. The selected family is per UI session, not an account-level `activeFamily`. Every fetch/mutation/media path retains explicit `familyId` and server ACL. On access loss, return to Hub with notice while keeping other family entries available. Query cancellation/generation guards prevent late A data from painting B.
6. Unread count updates on Hub entry, return, successful seen confirmation, invite/permission changes and foreground resume. While Hub visible, task §8.5 specifies a 30-second nonoverlapping refresh; stop in background. Preserve last confirmed count with stale indication or hide unavailable value. Never decrement per observer callback without server reconciliation.
