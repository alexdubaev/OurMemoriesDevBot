# Блок 11 — Финальная приёмка и закрытый запуск

**Исполнитель:** Sol. **Ревью:** Отдельный Sol review + ручная приёмка владельцем на телефоне.
**Зависимости:** 10 приняты и слиты в main.
**Цель:** Выпустить подтверждённый минимальный продукт для организатора и нескольких приглашённых семей.
**Правила работы:** корневой `AGENTS.md`; `../PARALLEL_WORK.md`; для UI также `../ASSET_GUIDE.md`.
**Спецификация:** `../00_START_HERE.md`; дополнительно прочитать: 07_DELIVERY.md, 09_ACCEPTANCE.md, design.md §D19, review/RELEASE_CHECKLIST.md.
**Стек:** выбранный Vibe — Bun/Hono, PostgreSQL/Prisma, React/Vite, общие Zod-контракты.

## Границы
Этот блок — единица сдачи, но внутри выполнять маленькие шаги и сохранять контрольные результаты. Пакет содержит спецификацию; пути ниже — ожидаемые создаваемые/изменяемые файлы, не утверждение их наличия до начала. Если аналогичный файл уже существует по REPO_MAP, использовать его и указать mapping, не создавать дубль. Все пути относятся к корню проекта.

MVP: только личный бот, Telegram Mini App, четыре формата, full/viewer, семейные лайки. Без AI, групп, платежей и реализации будущих платформ. Новые семейные данные — только synthetic fixtures до приёмки закрытого пилота.

## Файлы
Конфигурация только выбранного deployment-профиля; CI workflow; release manifest; runbook; review/RELEASE_REPORT.md. Исправления кода ограничены найденными блокерами.

## Потребляемые и производимые интерфейсы
Потребляет готовый код и спецификацию. Производит версионированный релиз с image digest, frontend hash, списком миграций и фактическим отчётом проверок.

## Порядок выполнения
1. Согласовать с владельцем провайдера, регион, бюджет, домен, credentials бота, оператора, поддержку и политику. Не покупать ресурсы и не придумывать эти данные.
2. Запустить FULL на точном чистом commit. Собрать один раз, развернуть staging, выполнить живые проверки в Telegram iOS/Android на синтетических материалах. Проверить отсутствие dev-login и fixtures в production.
3. Пройти все критерии09_ACCEPTANCE, визуальные состоянияD19, две роли и разные семьи. Браузерные тесты не объявлять доказательством работы телефона.
4. Убедиться в наличии restore evidence, TLS, private bucket, шифрования at rest и закрытой от интернета PostgreSQL. Настроить тревоги на очередь и устаревший backup.
5. Выполнить migration → API/worker → frontend одного release candidate. Webhook не удаляет pending updates. После релиза повторить smoke и сравнить hashes.
6. Показать владельцу лимиты пилота: одна семья на пользователя, один профиль ребёнка,2ГиБ private-storage для фото/служебных медиа; новые voice/video — только через личного бота и video остаётся Telegram-only без backup-обещания. Уже доставленное Telegram video нельзя отозвать из личного чата. Нет AI, групп и платежей. Только затем пригласить3–10семей.
7. На двухнедельном пилоте собирать частоты успеха, ошибок и обратную связь без копирования семейного содержимого в аналитику. Масштабирование и монетизация не объявляются готовыми.

## Обязательные сценарии проверки
F11.1 Чистая установка, миграции и сборка воспроизводимы. F11.2 Пройдены всеP01–P24. F11.3 Проверены потеря сети, отзыв роли и клавиатура. F11.4 Dev-route отсутствует. F11.5 Выпущенные hashes соответствуют кандидату. F11.6 Остановка worker корректна с pending jobs. F11.7 Откат кода совместим со схемой; restore БД не используется как обычный rollback.

## Проверочный цикл каждого изменения
- [ ] Найти существующие границы и перечислить затронутые файлы до редактирования.
- [ ] Для каждого сценария выше написать или уточнить тест на ближайшем подходящем уровне.
- [ ] Запустить новый тест до реализации и убедиться, что падение относится к нужному поведению, а не к случайной ошибке окружения.
- [ ] Реализовать минимальное изменение в указанном модуле, не менять контракт без согласования его потребителей.
- [ ] Запустить тот же тест, затем связанные проверки из плана области влияния.
- [ ] Проверить diff и выполнить самостоятельный review. При назначенном Sol review получить отдельный проход без опоры только на отчёт исполнителя.
- [ ] Записать команды, результаты и ограничения в отчёт по `../review/BLOCK_REPORT.md`.
- [ ] Передать владельцу результат и остановиться до следующего блока. Commit — в своей ветке, без автоматического merge/deploy.

## Команды проверки
Новые тестовые файлы с указанными именами создаёт этот блок. Фильтр должен реально находить тесты: ноль найденных тестов не является успехом. Если выбранный Vibe использует другую эквивалентную команду, обновить REPO_MAP/verification-map и привести фактический запуск.
```bash
bun run architecture:check
bun run typecheck
bun run test:contracts
bun run test:backend
bun run test:webapp
bun run build:webapp
bun run build:backend
bun run e2e:webapp
```

## Что показать владельцу
Владелец лично отправляет четыре формата, приглашает full/viewer, проверяет сердечко, подпись голоса и удаление. Другая тестовая семья не получает файлы по подставленному ID.

## Критерий готовности
НетP0/P1; все обязательные проверки пройдены, иначе релиз BLOCKED. Pending и skipped не обозначаются как pass.

## Стоп-условия
Не открывать публичную регистрацию, не подключать Stars, AI или группы. Недостающие operator/credentials/правовые данные блокируют деплой, но не локальную разработку.

Невозможность запустить обязательный тест отмечается `BLOCKED` с причиной; не заменять его проверкой синтаксиса. Успех в локальной БД не доказывает готовность production-конфигурации.

## CI не начинается с нуля в релизе
Базовый PR verify-required уже создаётся блоком00. Здесь расширяется проверка финального active scope и добавляется подтверждаемый release workflow; не ломать существующие protections и не переименовывать required check без согласованного обновления правила.
