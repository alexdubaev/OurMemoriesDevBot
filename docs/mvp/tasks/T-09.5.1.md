Наблюдения о коде в разделе 15 относятся только к этому snapshot, а не к актуальному GitHub или состоянию production. Источники приведены в приложении A.

Перед реализацией coding-агент сверяет ТЗ с актуальным `main`, `AGENTS.md`, существующими worktree и уже принятыми изменениями. Не откатывает код к исследованному SHA. Наличие у coding-агента доступа к GitHub не означает, что координатор выполнил свежую проверку репозитория.

Позднейшее прямое решение владельца имеет приоритет над старым ограничением «одна активная семья на пользователя» и ручным допуском создателей к пилоту. Новое ТЗ меняет только перечисленные ниже правила. Оно не отменяет остальные границы MVP и правила приватности.

### 0.1. Явно принятые продуктовые решения

1. Любой пользователь после действующего входа может создать собственную семью без приглашения в пилот и без ручного разрешения организатора.
2. В чужие семьи пользователь входит по семейным приглашениям. Создание собственной семьи не даёт доступа к чужим данным.
3. Один аккаунт может одновременно иметь собственную семью и участвовать в других. Взаимные приглашения должны работать в любом порядке.
4. После обычного запуска и авторизации открывается стартовый экран «Мои семьи», а не скрытый переключатель в настройках.
5. На стартовом экране видны собственная семья, когда она есть, и семьи, к которым пользователь присоединился.
6. Пользователь без собственной семьи, например бабушка, видит семьи близких и не обязан создавать свой альбом.
7. У каждой семьи отображается персональный счётчик непросмотренных воспоминаний.
8. Реализация ведётся блоками; новые возможности не должны ломать работающие процессы.

### 0.2. Уточнения первой версии ТЗ

Следующие правила конкретизируют обсуждённую модель и утверждаются вместе с документом: не более одной собственной неудалённой семьи; несколько чужих семей; отсутствие массового счётчика старого архива при первом вступлении; критерий просмотра карточки; начальные интервалы обновления; обработка незавершённых действий и неоднозначной публикации через бота. Это проектные решения ТЗ, а не утверждения о существующем поведении.

## 1. Цель и пользовательский результат

Создать единую точку входа в доступные пользователю приватные семейные альбомы. Пользователь должен понимать, какие семьи ему доступны, в какой семье он находится и где появились новые воспоминания.

Ключевой сценарий: Александр создаёт свою семью, другой человек создаёт свою, затем они приглашают друг друга. Каждый остаётся владельцем собственного альбома и получает отдельно назначенные права в другом.

Второй сценарий: бабушка участвует в семьях Миши, Саши и Лены. При запуске видит три различимые карточки со счётчиками, открывает нужную ленту и возвращается к списку. Собственного альбома у неё может не быть.

Целевой путь обычного использования:

`Вход → Мои семьи → Лента выбранной семьи → Все семьи`.

Это не общая лента всех родственников. Фотографии, дети, участники, приглашения, хранилище и права разных семей не объединяются.

## 2. Границы задачи

### 2.1. Входит

- Открытое создание собственной семьи после существующей авторизации.
- Несколько действующих членств одного пользователя с раздельными правами.
- Сохранение и расширение существующих семейных приглашений для этого сценария.
- Стартовый экран «Мои семьи» и возврат к нему из выбранной семьи.
- Корректный жизненный цикл выбранного семейного контекста.
- Серверное состояние просмотренных воспоминаний и персональные счётчики.
- Режим «Непросмотренные» в существующей ленте.
- Однозначный выбор семьи для публикации через действующие бот-каналы.
- Совместимость контрактов, миграции, целевые тесты и безопасное включение функции.

### 2.2. Не входит

- Отдельные приглашения в приложение, коды допуска в пилот, их админ-панель.
- Публичный поиск семей, открытые альбомы, общий каталог пользователей.
- Несколько собственных семей одного аккаунта в первой версии.
- Новая система аккаунтов, принудительные пароли, passkey или повторная регистрация для каждой семьи.
- Новые роли, автоматическое повышение прав и расширение прав загрузки видео.
- Чат, комментарии, отчёты «кто посмотрел», push-уведомления, массовые рассылки.
- Несколько профилей детей внутри одной семьи, новый редактор семейных аватарок.
- Общий redesign, массовый CSS-refactor, изменение палитры или всего набора компонентов.
- Переписывание media pipeline, новый recorder/player, массовое обновление зависимостей.
- Возобновление диагностического PR #77 или исправление private media по недоказанной гипотезе.

«Поделиться memoLy» означает отправку обычного публичного адреса приложения без доступа к семейным данным. Специальный реферальный механизм для этого не нужен; новый share-интерфейс не является обязательной частью данного ТЗ.

## 3. Аккаунт, собственная семья и членства

### 3.1. Один аккаунт

Все семьи принадлежат контексту одного существующего пользователя. MAX и PWA, связанные штатным механизмом входа, должны видеть одинаковые членства и состояние просмотра. Существующий Telegram-вход сохраняется в поддерживаемом проектом объёме.

Не создавать второй аккаунт при принятии второго приглашения. Не объединять аккаунты по совпадению имени, фотографии или непроверенного внешнего идентификатора. Межпровайдерное связывание, которого нет в текущем продукте, не добавлять как скрытую зависимость.

Открытое создание означает отсутствие ручного допуска, но не анонимную запись в API: действующая сессия и текущие проверки безопасности обязательны. Статус владельца семьи не делает пользователя администратором memoLy.

### 3.2. Собственная семья

В первой версии у пользователя не более одной собственной неудалённой семьи. Собственной считается семья, владельцем которой он является по серверной модели, а не любая семья с правом публикации.

Семья в процессе удаления продолжает занимать этот слот до завершения действующего процесса удаления. ТЗ не добавляет новый процесс удаления или передачи владения. Незавершённое заполнение профиля ребёнка тоже не освобождает слот: пользователь продолжает оформление уже созданной семьи.

Проверка ограничения выполняется сервером и выдерживает два одновременных запроса с разных устройств и разными ключами идемпотентности. Одна лишь блокировка кнопки или предварительный SELECT не считается защитой от гонки.

### 3.3. Семьи близких

Можно иметь несколько действующих членств в чужих семьях. Пример с тремя семьями не задаёт максимальный лимит «три». Новый произвольный лимит участия этим ТЗ не вводится.

Членство уникально для пары «пользователь — семья». Повторное принятие приглашения не создаёт вторую карточку той же семьи. Участие в чужих семьях не препятствует созданию собственной и не занимает её слот.

### 3.4. Права независимы

Сохраняется текущая серверная модель ролей и полномочий. В исследованном коде роли — `full` и `viewer`, а владение определяется отдельно через `ownerUserId`; новые роли «editor/admin семьи» из текста придумывать нельзя [S03, S04].

Для каждого действия права проверяются в целевой семье. Владелец семьи A, приглашённый с просмотром в семью B, не может публиковать, редактировать, приглашать или управлять B сверх её действующих разрешений.

Изменение роли либо отзыв доступа в A не меняет членство в B. Пользователь не получает доступ ко всем семьям человека только потому, что вступил в одну из них. Не приглашать организатора приложения автоматически в созданные альбомы.

### 3.5. Лимиты ресурсов

Снятие допуска к пилоту не означает отмену квот хранилища, ограничений размера/типа файлов, rate limits и других существующих защит. Не выдавать ресурсы сверх текущей конфигурации и не создавать платную инфраструктуру.

Если в актуальном коде обнаружен общий технический предел количества семей, отделить его от ручной авторизации в пилот. Описать поведение при исчерпании ресурса; не оставлять скрытое требование персонального разрешения и не снимать ресурсный предел без решения владельца.

## 4. Создание семьи и семейные приглашения

### 4.1. Обычная ссылка на приложение

Неавторизованный человек проходит существующий вход. После входа без специальной ссылки открывается «Мои семьи». Если семей нет, там доступна кнопка «Создать свою семью».

Проверку `pilotAdmission` как обязательного допуска к созданию убрать. Не удалять историческую таблицу и данные допусков только ради этой задачи. Не снимать другие проверки авторизации, блокировки аккаунта и доступа [S01].

### 4.2. Создание

1. Проверить на сервере право создания и отсутствие собственной неудалённой семьи.
2. Создать семью и членство владельца в согласованной транзакции с идемпотентностью.
3. Открыть существующее оформление профиля ребёнка, сохранив его валидацию, фотографию, crop и обработку конфликтов.
4. После завершения открыть ленту созданной семьи; она также присутствует на стартовом экране.

Имя семьи задаётся существующим способом. При использовании общего имени по умолчанию карточка должна оставаться различимой благодаря подписи. Новое обязательное поле, которого нет в текущем процессе, без визуального согласования не вводить.

Ошибка сети не означает, что семья не создана. Повтор должен восстановить результат той же операции, а не создать дубликат. Если создание успешно, а профиль не заполнен, показывать собственную семью со статусом «Завершить настройку».

Достигнутый лимит собственной семьи объяснять именно как «У вас уже есть своя семья» с переходом к ней. Не возвращать старое общее «Вы уже состоите в семье» для любого членства. Различать конфликт владения, повтор операции и другие ограничения БД; не маскировать все unique-ошибки одним семейным отказом.

Пользователь может вернуться ко всем семьям из незавершённого оформления своей семьи и открыть чужую. Не запирать его в onboarding при наличии других доступных альбомов. Несохранённые изменения обрабатывать по разделу 7.3.

### 4.3. Вступление по приглашению

Сохраняются текущие выпуск, назначение роли, необязательное имя участника, copy/share, срок, одноразовость, отзыв, preview и серверное принятие семейного приглашения. Новое изменение — существующее членство в другой семье больше не является отказом.

Действие ссылки относится только к указанной семье. Не выводить ошибку `OTHER_FAMILY` лишь потому, что пользователь уже имеет свою или чужую семью. Не требовать выхода из неё, logout, удаления PWA или нового аккаунта.

Существующий подтверждённый сценарий принятия по платформам сохраняется: где действует предварительный экран подтверждения, оставить его; где согласован вход с автоматическим принятием в browser/PWA, не добавлять лишний барьер. Само новое ТЗ не разрешает незаметно менять этот UX. В snapshot эти ветки различаются [S05].

После успешного принятия обновить список членств, открыть приглашённую семью либо её существующее целевое состояние и предоставить путь «Все семьи». Приглашение не должно теряться за стартовым экраном или за предложением создать собственную семью.

### 4.4. Повторы, ошибки и отзыв

- Повтор той же успешной операции тем же действующим участником безопасен; второй записи членства нет.
- Приглашение для уже действующего участника не используется как способ сменить его роль. Изменение роли остаётся отдельной авторизованной операцией.
- Использованная другим человеком, истёкшая или отозванная ссылка показывает существующую понятную ошибку и не меняет ни одну семью пользователя.
- Отзыв доступа не отменяется повторным открытием старой уже использованной ссылки. Для повторного вступления нужно новое действующее приглашение по существующим правилам.
- Отмена пользователем принятия не затрагивает его собственную семью.
- Лимит участников конкретной семьи, если он действует, проверяется и при конкурентном принятии.
- Встречные приглашения не принимаются автоматически друг за друга.

### 4.5. Обязательный взаимный сценарий

| Семья | Александр | Второй пользователь |
|---|---|---|
| Семья Александра | Владелец | Назначенные приглашением права |
| Семья второго пользователя | Назначенные приглашением права | Владелец |

Проверить два порядка: «сначала создал свою → вступил в чужую» и «сначала вступил в чужую → создал свою». Результат одинаков; данные семей не копируются.

## 5. Стартовый экран «Мои семьи»

### 5.1. Место в приложении

Это основной авторизованный стартовый экран, а не функция в настройках. Он показывается и при одной доступной семье: намеренный дополнительный тап ради единой понятной точки входа.

При наличии собственной семьи: раздел «Моя семья» с её карточкой, ниже непустой раздел «Семьи близких». Пустые секции не выводить. При отсутствии собственной семьи: общий заголовок «Мои семьи» и список доступных альбомов без пустой карточки или предупреждения «У вас нет семьи».

Кнопка «Создать свою семью» видна, пока собственного альбома нет. Если чужие семьи уже есть, действие компактное и вторичное. Если список пуст, создание — основное действие. Бабушка может пользоваться приложением, ни разу его не нажимая.

### 5.2. Карточка семьи

Содержит название, компактное изображение, подпись для идентификации, роль текущего пользователя при необходимости, счётчик новых воспоминаний и указатель перехода. Вся карточка нажимаема. Бейдж — не отдельная маленькая цель для попадания пальцем.

Использовать имеющийся аватар ребёнка через действующий приватный media flow. При отсутствии изображения — штатный fallback. Новый тип «фото семьи», загрузчик и crop для карточки не вводить. Сбой миниатюры не блокирует открытие семьи и не превращает счётчик в ноль.

Названия «Семья Миши», «Семья Саши», «Семья Лены» — примеры, а не автоматически вычисляемое родство. Для одинаковых названий использовать доступную серверную подпись, например имя ребёнка/владельца. Не выдумывать имя или родственную связь; предусмотреть нейтральное различимое обозначение, если данных нет.

Своя семья всегда первая. Остальные — в стабильном порядке по названию с устойчивым дополнительным ключом. Изменение счётчика не переставляет карточки во время нажатия. Длинные названия, одинаковые подписи и длинный список должны быть обработаны макетом.

### 5.3. Счётчик в карточке

Смысл: количество новых для данного участника опубликованных воспоминаний, которые он ещё не просмотрел. Не количество сообщений бота, лайков, приглашений или непрочитанных текстов.

Положительное значение показывается небольшим числовым бейджем; ноль не показывается. Для больших значений визуально допустимо `99+`, при этом сервер сохраняет точное число. Доступное имя карточки передаёт смысл «Семья Миши, три новых воспоминания».

Неизвестное значение не равно нулю. При ошибке обновления сохранить последнее известное значение с состоянием устаревших данных либо показать отсутствие актуального значения без ложной цифры.

| FH-08 | Частичная ошибка/устаревшие счётчики, остальной список доступен |

| FH-10 | Семья стала недоступна, список остальных сохранён |
| FH-11 | Длинные/одинаковые названия, много семей, большие счётчики |
| FH-12 | Входящее приглашение поверх приоритетного маршрута входа |
| FF-01 | Обычная лента выбранной семьи и возврат «Все семьи» |
| FF-02 | Режим «Непросмотренные», включая пустой результат |
| FF-03 | Предупреждение о несохранённых изменениях перед выходом из семьи |

Не превращать эти состояния в новые отдельные страницы без необходимости. Визуально переиспользовать компоненты и шесть текущих тем. Для текстового этапа достаточно этого каталога; новые макеты ещё не считаются утверждёнными.

## 6. Запуск, ссылки, возврат и жизненный цикл

### 6.1. Приоритет стартового маршрута

1. Завершить действующий вход/восстановление сессии, когда требуется.
2. Обработать явное назначение запуска: семейное приглашение, существующую ссылку на воспоминание, подтверждение browser-link или подтверждённый контекст публикации.
3. При отсутствии явного назначения открыть «Мои семьи».

Этот приоритет не создаёт новые типы deep link, которых нет в приложении. Он запрещает ломать уже поддерживаемые. Обычная ссылка на чужое воспоминание сама по себе не является приглашением и не выдаёт доступ.

### 6.2. Новый запуск и возобновление

Обычный запуск по корневому адресу/иконке приложения ведёт на список семей. Не восстанавливать последнюю семью молча вместо стартового экрана.

Возврат из фона в существующую сессию сохраняет открытый экран, scroll и воспроизведение в пределах поведения платформы. `visibilitychange` сам по себе не повод сбросить приложение на «Мои семьи». Перезагрузка явного поддерживаемого адреса учитывает назначение этого адреса.

Не пытаться угадывать «новый запуск» по модели телефона. Правила применяются к намерению маршрута и жизненному циклу приложения. Настроить и проверить одинаковую логику в MAX, PWA и поддерживаемом Telegram-контексте.

### 6.3. Навигация внутри семьи

Открытие карточки ведёт в существующую ленту семьи; незавершённая собственная семья ведёт к продолжению настройки. Из ленты и корневого семейного экрана доступно явное «Все семьи», не требующее открытия настроек.

Нижняя навигация «Лента / Добавить / Семья» работает внутри выбранной семьи. На стартовом списке не показывать кнопку добавления без однозначной семьи назначения. Не заменять существующую стрелку профиля ребёнка переключением семей.

Back сначала закрывает modal/detail/редактор по текущим правилам, затем возвращает на предыдущий экран и к списку семей. Возврат к «Моим семьям» не должен сразу повторно открыть обработанную ссылку приглашения.

После выхода из аккаунта очистить семейный контекст, запросы и персональные отметки клиента. Не показывать новому пользователю закэшированный список предыдущего аккаунта.

## 7. Изоляция выбранной семьи и незавершённых действий

### 7.1. Контекст просмотра

Выбранная семья — локальное состояние навигации конкретной сессии интерфейса, а не новая глобальная принадлежность аккаунта. Выбор на телефоне не переключает самостоятельно другую открытую PWA-вкладку.

Каждый семейный запрос содержит проверяемый `familyId`. Клиентское значение не является полномочием: сервер проверяет актуальное членство и нужное действие. Нельзя выбирать семью на сервере через произвольное `findFirst()` по пользователю.

### 7.2. Переключение A → B

Запросы, query keys, списки, курсоры, optimistic updates, аватары, роли, child context, sheets и выбранные воспоминания разделены как минимум по аккаунту и семье; фильтры и курсоры добавляются там, где нужны.

Поздний ответ A не должен попадать в UI B. Старые family-запросы отменяются или их результат игнорируется по ключу/поколению контекста. Нельзя на мгновение выводить права владельца A над данными B.

При потере доступа к A остановить её polling и чтение медиа, закрыть её детали, удалить доступный клиенту кэш A и вернуться к списку с понятным сообщением. Не вылогинивать пользователя из остальных семей и не очищать их подтверждённые данные без необходимости.

### 7.3. Формы и загрузки

Открытая форма и начатая операция всегда привязаны к семье, ребёнку и автору на момент начала. Переключение интерфейса не переписывает получателя операции.

При несохранённом тексте/настройках перед выходом предложить остаться либо отказаться от изменений. Не вводить серверные черновики и долгоживущий offline composer ради этого ТЗ.

Если текущая загрузка допускает безопасное продолжение вне экрана, она завершается только в исходной семье. Если не допускает — блокировать уход понятным сообщением или использовать существующую безопасную отмену. Молчаливое исчезновение загрузки, повторная публикация в B и перенос резервирования квоты в B запрещены.

В composer показывать семью назначения, например «Добавляем в семью …». В режиме редактирования цель неизменна; перенос воспоминаний между семьями не входит в задачу.

Тема остаётся существующей пользовательской настройкой с серверным источником истины. Не заводить отдельные темы на каждую семью и не возвращать конфликтующие значения из legacy localStorage.

## 8. Непросмотренные воспоминания: точная семантика

### 8.1. Что считается новым

Единица счёта — опубликованное воспоминание `Memory`: фото, видео, голос или заметка. Несколько вложений одной публикации считаются одной единицей.

Непросмотренной для пользователя считается запись, которая одновременно:

1. Доступна ему в данной семье по текущим правилам.
2. Находится в опубликованном, не удалённом состоянии и доступна в ленте.
3. Впервые опубликована после персональной границы начала учёта.
4. Создана не самим этим пользователем.
5. Не имеет подтверждённой сервером отметки просмотра этим пользователем.

Формально: `count(user, family) = число доступных новых публикаций без отметки seen`, а не разница между общим количеством карточек и номером последней посещённой страницы.

При backdated-публикации дата съёмки/события `occurredAt` не определяет новизну. Фото за январь, опубликованное сегодня, может быть новым. Изменение подписи, даты, лайк или повторная доставка того же source не создают новую единицу.

Удалённая публикация исключается из числа и режима непросмотренных. Неопубликованная загрузка/черновик не входит в число. Если запись создаётся раньше, чем впервые становится доступной в ленте, новизна отсчитывается от первого опубликованного состояния, а не автоматически от создания строки. Последующее обновление уже опубликованного preview не является повторной публикацией. Ошибка загрузки конкретного изображения у клиента не делает опубликованную запись просмотренной.

### 8.2. Начальная граница учёта

При первом вступлении существующий архив доступен, но не попадает массово в новые. Граница фиксируется сервером при успешном вступлении, а не при первом открытии списка через неделю. После вступления новые публикации учитываются, даже если пользователь ещё не заходил в ленту.

Для существующих участников при первом включении функции устанавливается единая согласованная граница миграции/активации: весь более ранний архив считается историческим. После этого счётчики уже не переинициализируются при каждом входе, deploy или новом устройстве.

При повторном вступлении после отзыва по новому приглашению формируется новая граница участия: архив до повторного вступления не превращается в массовое непросмотренное. Старый retry просмотра не должен менять новую эпоху членства.

Публикация, одновременно обрабатываемая со вступлением/активацией, должна иметь однозначный результат. Нельзя терять новое событие из-за сравнения клиентских часов, округления timestamp или принятия выделенного sequence за порядок commit. Реализацию границы и её гонок зафиксировать в блоке B0 и проверить в B4; предпочтительно использовать существующую модель публикации, не строить вторую ленту.

### 8.3. Что означает «просмотрено»

Это отметка знакомства с карточкой, а не доказательство прочтения текста или досмотра видео. Пользователь не должен открывать каждую фотографию fullscreen и запускать каждое голосовое ради исчезновения бейджа.

Отметка может создаваться, когда основное содержимое успешно отрисовано и устойчиво видно в активном, незакрытом другим экраном интерфейсе. Не засчитывать prefetch, виртуализированную карточку вне экрана, заглушку загрузки, неуспешно полученную фотографию или фон за полноэкранным/modal-слоем.

Начальный измеримый критерий для первой версии: основная область карточки видна непрерывно не менее 1 секунды и занимает не менее 50% от меньшей из двух высот — самой области и доступного видимого viewport. Горизонтальное содержимое также должно быть в видимой зоне. Это параметр продукта, не измерение внимания пользователя; изменение параметра фиксируется в одном месте и тестируется.

Такой критерий учитывает высокие портретные фото: нельзя требовать показать 50% всей длинной карточки, когда её высота в несколько экранов. По возможности наблюдать содержимое, а не header/кнопку лайка. Доступная область учитывает перекрывающие панели и fixed-навигацию; одной проверки `isIntersecting` недостаточно.

Для фото нужно реально отображённое изображение. Для видео достаточно готового постера/корректного preview, для голоса — готовой карточки доступной записи, для заметки — текста. Воспроизведение и скачивание полного видео/голоса для отметки не требуются. Ошибочная карточка с недоступным основным содержимым автоматически не отмечается.

Полноэкранный просмотр или detail также может отметить именно открытую запись после готовности содержимого по тому же принципу. Карточки ленты под modal при этом не отмечаются.

### 8.4. Персональное серверное состояние

Подтверждённые отметки хранятся на сервере по пользователю, семье и воспоминанию с учётом текущего периода членства. Другие участники их не видят; не добавлять просмотр автором списка зрителей.

MAX и PWA одного аккаунта получают одинаковый результат после синхронизации. Повторная отметка идемпотентна. Одновременные просмотры на двух устройствах не дают отрицательный счётчик и не увеличивают его обратно.

Нельзя реализовать всё единственной отметкой «последний заход в семью» или «максимальная просмотренная дата»: пользователь может пропускать карточки и смотреть их не по порядку.

После восстановления связи неподтверждённые отметки можно повторить в рамках той же сессии и того же аккаунта. Пакеты имеют фиксированные family/membership identifiers; переключение семьи их не переписывает. При logout/отзыве доступа соответствующую очередь отменить. Сохраняемый offline-архив и долговременная offline-очередь не требуются.

### 8.5. Обновление счётчиков

Обновлять при входе на стартовый экран, возврате из семьи, успешном подтверждении просмотров, принятии приглашения, изменении доступов и возобновлении приложения. Пока список видим, использовать лёгкое периодическое обновление; стартовый интервал — 30 секунд. В фоне polling остановить; запросы не наслаивать.

Второй открытый контекст получает актуальные данные на следующем обновлении/возобновлении. Не обещать мгновенный push. Поздний ответ старого запроса не должен вернуть уже подтверждённый устаревший счётчик.

Серверный снимок значений и подтверждения отметок — источник истины. Допустим optimistic UI с последующей сверкой, но нельзя бесконтрольно выполнять `count--` на каждый callback наблюдателя.

Ошибка счётчиков не блокирует список семей, вход в ленту, загрузку или просмотр медиа. В первой версии не добавлять WebSocket, Redis, новые очереди или сервис аналитики только ради бейджей.

## 9. Режим «Непросмотренные» в существующей ленте

Показать компактное действие «Непросмотренные · N» для выбранной семьи, когда соответствующее число известно и положительно. Оно включает фильтрацию уже существующей ленты, а не открывает новый тип галереи.

Фильтр непросмотренности независим от текущих типов «Все / Фото / Видео / Голос / Заметки» и комбинируется с ними. Число N у действия обозначает все непросмотренные в семье; при выбранном типе пустой результат объясняется явно, без выдачи общего числа за количество этого типа.

При входе в режим запросить записи с сервера: фильтрация только уже загруженной первой страницы недостаточна. Сохранить существующую хронологию по дате события и корректную пагинацию, включая записи, опубликованные задним числом.

После засчитывания карточки не удалять её внезапно из-под пальца и не сдвигать scroll. Результат текущего просмотра стабилен; отмеченные записи можно оставить до выхода/явного обновления с локальной отметкой. Серверный счётчик уменьшается независимо от сохранения карточки на экране.

Пагинация выдерживает изменение seen-состояния, удаления и новые публикации. Не использовать offset с пропусками из-за исчезающих строк. Область курсора включает пользователя, семью, фильтры и необходимые параметры снимка; курсор другой семьи/пользователя не принимается.

Когда непросмотренных больше нет, показать спокойное сообщение «Все новые воспоминания просмотрены» и переход «Показать все». Не добавлять автоматическое «отметить всё» при открытии семьи. Массовая кнопка «Прочитать всё» в этот этап не входит.

## 10. Публикация из приложения и бота

### 10.1. Главный инвариант

**Просматриваемая семья и семья назначения публикации — разные понятия. Просмотр чужого альбома никогда молча не меняет получателя отправки через бота.**

В webapp composer получает конкретный family/child context при открытии. В ботах выбор определяется конкретной входящей отправкой и актуальными правами. Общая настройка «куда писать по последней открытой семье» запрещена.

### 10.2. Выбор для входящего сообщения боту

Кандидаты — семьи с действующим членством, разрешением на данный тип публикации и готовностью текущего профиля/сценария. Семья с правом просмотра не добавляет неопределённость. Право загрузки видео не выводится автоматически из наличия собственной семьи или имени роли: использовать фактическую действующую policy.

| Допустимые семьи | Поведение |
|---|---|
| Нет | Понятно сообщить, почему публикация недоступна; ничего не публиковать |
| Одна | Продолжить существующую автоматическую публикацию в неё; в результате назвать семью |
| Несколько | До публикации явно спросить, в какую семью добавить именно эту отправку |

Выбор предъявляется в текущем поддерживаемом бот-канале штатным способом с названиями доступных семей. Идентификатор выбора связывается с авторизованным пользователем и конкретной входящей отправкой; чужая кнопка/подделанный callback не могут назначить семью. Конкретную интеграцию с существующими adapter callbacks зафиксировать в B0/B3; не добавлять новый мессенджер или отдельного бота.

Не реализовывать правило `memberships[0]`, выбор любой первой семьи с `full`, приоритет владельца без проверки кандидатов или отправку сразу во все семьи. Каждое новое неоднозначное сообщение требует выбора; долгоживущая настройка предпочтительной семьи в этот этап не входит.

### 10.3. Ожидание выбора и фиксация цели

Входящая отправка может быть в состоянии ожидания выбора, но ещё не опубликована. Использовать существующий безопасный durable ingress/outbox и минимальные метаданные. Не создавать временное публичное медиа и не присваивать файл произвольной семье, чтобы потом перенести.

Окно ожидания выбора ограничено сервером; начальное значение для UX — 15 минут, без обещания, что внешнее медиа гарантированно доступно столько времени. Доступность provider source проверяется штатным способом при продолжении. При истечении выбора/источника сообщить об этом и предложить повторную отправку; не угадывать семью.

После выбора familyId и childId закрепляются за source/pending operation. Перезапуск worker, retry, переключение экрана, позднее вступление в другую семью и второй callback не меняют цель. После успешной публикации повтор callback возвращает существующий результат, не создаёт копию.

Если право в выбранной семье отозвано до публикации, завершить операцию понятным отказом; не перенаправлять в оставшуюся подходящую семью автоматически. Для сознательной новой отправки пользователь снова выбирает цель.

Для альбома/сгруппированной отправки выбор относится к существующей единице source-публикации целиком. Не разносить вложения одной публикации по семьям. Порядок выбора для двух одновременных сообщений может быть разным, но их цели и содержимое не смешиваются.

### 10.4. Уже известная цель и существующие процессы

Прямой upload из приложения и операция с уже подтверждённым family context не требуют второго вопроса только из-за нескольких членств. Если используется подписанный handoff, контекст проверяется сервером и сохраняется до конца.

Простой переход из приложения в личный чат с ботом ещё не является подтверждённой привязкой следующего сообщения к семье. Для действующих bot-handoff сценариев, включая голос, проверить реальную корреляцию: либо цель надёжно связана с конкретной операцией, либо при неоднозначности срабатывает явный выбор из раздела 10.2. Не обещать в интерфейсе публикацию в B, когда бот может автоматически выбрать A. Нельзя использовать неограниченное по времени правило «следующее любое сообщение относится к последней открытой форме».

Ответ на запрос подписи относится к исходному воспоминанию/семье по сохранённой связи, а не к текущему выбору интерфейса. Сохранить caption association, edit/reply, идемпотентность входящих событий и delivery acknowledgements.

После определения цели используется существующий publisher, private media acquisition, media ACL, резервирование/учёт квоты, обработка и playback. Допускаются минимальные изменения выбора scope и проверок неоднозначности, но не новый параллельный pipeline. Переслать источник в другую семью или скопировать уже опубликованную память этим ТЗ не разрешается.

Все действующие single-family сценарии остаются без дополнительного выбора. Несколько viewer-членств не должны ломать единственную разрешённую публикацию.

## 11. Данные, контракты и безопасность

### 11.1. Минимальные логические сущности

Точное именование таблиц/полей определяется в B0/B1 по текущему коду; обязательны следующие смыслы:

- Список доступных семей пользователя с ролью, признаком владения, состоянием настройки и данными карточки.
- Отдельная проверяемая возможность создать собственную семью, не равная отсутствию всех членств.
- Период действующего членства и граница начала учёта новых публикаций.
- Идемпотентные персональные отметки просмотра конкретных воспоминаний.
- Подтверждённая цель входящей source-операции и, когда нужно, состояние ожидания выбора.

Предпочтение — расширению существующего модульного монолита и его моделей. Не заводить копию семей, вторую сущность воспоминания, отдельный auth runtime и generic notification subsystem.

### 11.2. Требуемые операции API

| Операция | Обязательный результат |
|---|---|
| Получить семейный стартовый контекст | Только доступные семьи, собственная семья, capability создания, данные карточек |
| Получить счётчики | Значения только текущего пользователя по доступным семьям, различимое состояние неизвестности/ошибки |
| Создать семью | Одна собственная семья, независимо от viewer/full-членств в чужих |
| Принять семейное приглашение | Добавление целевого членства без уничтожения существующих |
| Отметить просмотр | Идемпотентное принятие bounded-пакета в указанной семье/эпохе членства |
| Получить непросмотренные | Серверная фильтрация и корректный семейный cursor |
| Выбрать цель bot source | Авторизованный и неизменяемый выбор для одной ожидающей операции |

URI и DTO фиксируются до реализации потребителей. Нельзя добавлять поля в строгий старый контракт и считать это автоматически обратно совместимым. В snapshot `familyMeResponseSchema` использует `.strict()` и literal `activeFamiliesMaximum: 1` [S06].

Не превращать старое поле `activeFamily` одновременно в «единственное членство», «последний просмотр» и «цель бота». Для новой модели нужны однозначные названия и явная стратегия совместимости.

### 11.3. Серверные проверки

Счётчики, список, feed, detail, preview медиа, seen API, bot choice и публикация проверяют действующий доступ к соответствующей семье. Переданный userId не используется вместо пользователя сессии. Нельзя запросить чужое состояние просмотра.

Отмечать собственный просмотр разрешено и `viewer`, и `full`: это персональное состояние чтения, а не право изменять семейное содержимое. Не ставить на seen API требование публикации или владения, иначе основной сценарий бабушки не заработает.

Пакеты seen ограничены по размеру, дедуплицируются и проверяются. Чужие семейные ID отвергаются без утечки существования ресурсов. Поздний пакет на уже удалённые/недоступные записи не должен раскрывать содержимое или портить число. Точная форма атомарного/частичного ответа определяется контрактом и покрывается тестом.

Отзыв доступа закрывает новые чтения и записи, даже если интерфейс ещё показывает старую карточку. Уже показанное пользователю невозможно «стереть из памяти», но дальнейшее API/media-чтение должно прекратиться по действующей ACL.

Не писать токены, cookies, invite tokens, private URL, storage keys, содержимое файлов и семейную переписку в логи/PR/handoff. Диагностировать технические операции без семейных данных. Не создавать публичный endpoint ради аватарок на стартовом экране.

### 11.4. Производительность и устойчивость

Счётчики вычисляются/читаются по индексируемым серверным данным, а не загрузкой всех медиа/всех лент клиента. Избегать отдельного полного сканирования истории для каждой карточки и N+1 по семьям. Измерить запрос на репрезентативном объёме, выбранном по реальным лимитам пилота, не объявлять нагрузочный PASS по двум пустым семьям.

Seen updates пакетируются с ограничением размера; повторные observer callbacks не создают поток одинаковых записей. Бейджи и их сбои не должны задерживать основную публикацию или ухудшать работоспособность private media.

Если для публикационной границы требуется изменение транзакции publisher, это минимальная метаданная интеграция с отдельной проверкой гонок, не переписывание storage/download/decode. Счётчик не должен стать единственной точкой отказа всей ленты. При техническом отказе учёта нельзя ни безвозвратно потерять факт публикации для будущего счётчика, ни объявить несуществующую отметку подтверждённой: нужен восстанавливаемый путь на существующих данных/механизмах, а не best-effort событие только в памяти процесса.

## 13. Реализация по блокам

### 13.1. Общие правила блоков

Каждый блок имеет отдельное назначение, base SHA, allowed paths, краткую цель, контракты на входе/выходе и критерий завершения. По умолчанию блоки выполняются последовательно. Один исполнитель может вести их по очереди; восемь блоков не означают восемь параллельных агентов.

Начинать от принятого актуального `main`. Общие contracts/schema/composition root/route files меняет один назначенный владелец. Не начинать потребителя от непроверенной соседней ветки и не затирать чужие whole-file изменения.

После каждого блока — фактический HANDOFF и остановка. Следующий блок, merge и deploy требуют отдельного назначения. Независимое ревью, если назначено по риску, не выдаётся за self-review; без лишних субагентов и бесконечных QA-циклов.

### 13.2. Карта зависимостей

### B0 — Актуализация и фиксация стыков

**Сделать:** сверить текущий код; найти все single-family assumptions в API, auth projection, family bootstrap, ботах, background workers, тестах и UI; проверить текущие права каждого типа публикации. Зафиксировать реальные входы MAX/Telegram/PWA, приоритеты deep links, контракт списка семей, стратегию old-client compatibility и публикационной границы unread. Подготовить отдельный минимальный визуальный вариант состояний раздела 5.4, не меняя canonical.

**Не делать:** миграции production, массовый redesign, реализацию всех последующих блоков.

**Завершение:** владелец видит изменения контрактов/новых состояний; конфликтов с текущими принятыми процессами нет либо они явно закрыты решением. Baseline снят на конкретном SHA; известные исходные ошибки отделены от новых.

### B1 — Модель, контракты и управление включением

**Сделать:** минимальные новые таблицы/поля/индексы, ограничение одной собственной семьи, механизм нескольких членств, unread baseline/seen и нужные contracts. Расширения оставляют прежний путь работоспособным. Исторические миграции не редактируются.

**Особое условие:** снятие DB-индекса одной семьи само по себе не должно открывать пользователям новый сценарий до готовности B2–B7. Если индекс снимается на этой стадии, старый runtime guard продолжает действовать для несовместимых клиентов, а новый путь закрыт серверным gate.

**Проверки:** пустая тестовая БД и БД с существующими пользователями/семьями; неизменность данных, ролей, children/media relationships; гонка на собственную семью; старые и новые contract fixtures.

**Завершение:** совместимая схема и определённая стратегия включения; новых multi-family пользователей в production из одного этого блока быть не должно.

### B2 — Серверные семьи и приглашения

**Сделать:** открытое создание без pilot admission в новом целевом поведении, список семейств аккаунта, capability создания, безопасные повторные и встречные приглашения, отдельные права. Сохранить действующую обработку invite expiry/revoke и scope проверок.

**Проверки:** обе последовательности взаимного сценария, уже существующий участник, конкурентные create/accept, viewer в A и owner в B, отзыв только одного членства. Проверить требования авторизации нового пользователя через browser/PWA, не только native initData.

**Завершение:** API работает в тестовом окружении; multi-family activation остаётся закрытой до готовности всех потребителей.

### B3 — Бот и неизменяемая цель публикации

**Сделать:** все места определения семьи в действующих MAX/Telegram pipelines; zero/one/multiple candidates, pending choice, reply/caption association, фиксацию семейной цели. Явный webapp upload/handoff продолжает свой подтверждённый путь без повторного выбора.

**Не делать:** новый media engine, новый bot, смену ACL, чтение групп, массовые переработки capture/storage.

**Проверки:** single-family без лишнего вопроса; одна publish-семья плюс несколько viewer; две publish-семьи; разные права на типы; два одновременных source; retry/restart/duplicate callback; отзыв роли между выбором и publish; caption и video finalize; ни одного случайного назначения в другую семью.

**Завершение:** никакой поддерживаемый активный worker не полагается на «у пользователя ровно одно членство» и не выбирает первое произвольное. При неоднозначности без выбора публикации нет.

### B4 — Непросмотренные на сервере

**Сделать:** персональную границу, отметки seen, счётчики, серверный фильтр, курсоры и авторизацию. Определить начальную миграцию старого архива и межустройственное обновление.

**Проверки:** первая/повторная связь с семьёй; старый архив; delayed/backdated publish; конкурентный commit относительно join/activation; свои записи; удаление/редактирование; повторные seen и две сессии; неверные family/user/epoch; частичные сетевые повторы; пагинация меняющегося unread-множества; стоимость запросов.

**Завершение:** счётчик обоснован серверными данными; фото и лента не становятся зависимы от работоспособности счётчика.

### B5 — «Мои семьи» и выбранный контекст

**Сделать:** согласованные состояния стартового экрана, создание/возобновление собственной семьи, открытие приглашённой, возврат «Все семьи», запуск и deep links. Подключить реальные summaries/count DTO; не поставлять демонстрационные цифры или временные заглушки как готовый функционал.

**Проверки:** zero/one/many families, бабушка с тремя, незавершённая собственная, длинные названия, ошибки, все шесть тем в новом экране; family-scope queries/cache; поздние ответы и отзыв; unsaved composer; фон/возврат без сброса видео; отсутствие регрессий хедера и нижней навигации.

**Завершение:** все семейные действия имеют однозначную цель; нет кратковременного показа данных/прав другой семьи.

### B6 — Просмотры и режим непросмотренных

**Сделать:** клиентский критерий видимости/готовности, batching и acknowledgement seen, обновление бейджей, режим непросмотренных в реальной ленте. Оставить прежний механизм появления новых публикаций функционально отдельным от персонального счётчика.

**Проверки:** 7 → просмотр 2 → остаток 5; загрузка страницы без просмотра; фон/модальное перекрытие; очень высокое фото без crop; ошибка фото; video poster/voice без требования досмотра; два аккаунта и два контекста одного аккаунта; потеря сети; пагинация/скролл без скачков.

**Завершение:** цифры согласованы с сервером, просмотра чужим пользователем нет, показанные записи не исчезают под пальцем.

### B7 — Интеграция и выпуск

**Сделать:** интеграционную проверку общей функции на актуальном merge candidate; согласованный переход схемы/старых клиентов/worker; план включения и восстановления. Только после разрешения владельца — merge/deploy по действующему runbook и ручная проверка телефона.

**Проверки:** матрица раздела 14, обязательные project gates, поддерживаемые платформы по затронутому scope. Один общий интеграционный проход, а не полный QA после каждого CSS изменения.

**Завершение:** записаны фактические SHA, миграции, состояние feature gates, приёмка и оставшиеся ограничения. Невыполненные проверки не помечены PASS.

## 16. Миграции, включение и восстановление

### 16.1. Безопасная последовательность

1. Совместимая схема/контракты и выключенный новый путь.
2. Серверные операции, бот-обработчики и все активные consumers умеют несколько семей.
3. Новый UI, счётчики и deep links проверены вместе.
4. Проверена совместимость уже установленных PWA/кэшированных сборок и старых API consumers.
5. По отдельному разрешению — активация и инициализация границы непросмотренных.

Не включать возможность второго членства, пока хоть один активный путь бота/клиента не готов корректно его обрабатывать. Не трактовать «все PR merged» как разрешение production.

В B0 определить минимальное управление включением на сервере. Новую платформу feature flags не строить. Флаг не может быть чисто UI: старый клиент способен вызвать API напрямую.

### 16.2. Старые клиенты

В snapshot строгий contract не принимает произвольные новые поля. Предусмотреть версионирование или отдельный новый endpoint/ответ с явной capability. Старые клиенты с single-family DTO не должны молча выбрать случайную семью после второго членства.

При необходимости безопасно предложить обновить приложение до входа в несовместимый путь. Не лечить совместимость советом очистить все данные, удалить PWA или unregister Service Worker. Не переписывать SW lifecycle в составе этой задачи без подтверждённой необходимости и отдельной проверки.

### 16.3. Отмена включения не равна откату данных

До появления второго членства допустимость старого release определяется совместимостью схемы. После появления нескольких членств откат к старому коду с предположением одной семьи может сломать доступ и публикацию.

Отключение функции должно прежде всего останавливать новые несовместимые изменения, сохраняя безопасное обслуживание уже существующих multi-family пользователей. Нельзя спрятать список и вернуть `findFirst` как якобы rollback.

Не восстанавливать unique index одной семьи поверх новых данных; не удалять лишние членства/семьи для возможности отката. Сначала forward-fix либо заранее проверенная совместимая версия. Восстановление production backup — отдельное решение с пониманием потери новых записей.

Исторические миграции не править. Применённую колонку пользовательской темы не удалять. Таблицу `pilot_admissions` не чистить «за ненадобностью» без отдельной задачи.

### 16.4. Выпуск и приёмка

Деплой — только по действующему `AGENTS.md` и Selectel runbook после отдельного назначения. Проверить actual target SHA, migration status, frontend/backend health, новый и существующий односемейный сценарии. Не обходить dirty-checkout guard и не делать общий reset/clean.

Физическую проверку выполнить минимум на двух логических аккаунтах с синтетическими/разрешёнными материалами: две собственные семьи, встречные приглашения и независимые роли. Бабушкин сценарий — аккаунт без собственной семьи с тремя приглашёнными. Не рассылать реальные тестовые приглашения посторонним.

## 17. Критерий завершения задачи

Задача завершена, когда пользователь без допуска может создать свою семью; действующий участник чужой семьи не теряет её при создании своей; встречные приглашения работают; обычный старт показывает «Мои семьи»; счётчики персональны и достоверны; публикации идут только в однозначно выбранную семью; затронутые действующие процессы прошли регрессионную проверку.

Недостаточно закрыть только новый экран или убрать `already_in_family`. Не принимать задачу без bot routing, корректной ACL, совместимости контрактов и серверного unread-состояния. Новая графика без реальных данных не является реализацией.

Все обязательные проверки имеют фактический результат. Непроверенные платформы/состояния обозначены явно. Первопричину старого private-media сбоя не объявлять исправленной этой задачей.
