# Блок 08 — Онбординг, приглашения и права в интерфейсе

**Исполнитель:** Terra. **Ревью:** Sol — выдача/отзыв доступа и защита owner.
**Зависимости:** 04, 06 приняты и слиты в main. Разрешённая параллельная волна B; читать ../PARALLEL_WORK.md.
**Цель:** Организатор приглашает близких и управляет двумя уровнями доступа через понятный интерфейс.
**Правила работы:** корневой `AGENTS.md`; `../PARALLEL_WORK.md`; для UI также `../ASSET_GUIDE.md`.
**Спецификация:** `../00_START_HERE.md`; дополнительно прочитать: 01_PRODUCT.md §§3–4, design.md §§D14–D16, 03_DATA_API.md §5.
**Стек:** выбранный Vibe — Bun/Hono, PostgreSQL/Prisma, React/Vite, общие Zod-контракты.

## Границы
Этот блок — единица сдачи, но внутри выполнять маленькие шаги и сохранять контрольные результаты. Пакет содержит спецификацию; пути ниже — ожидаемые создаваемые/изменяемые файлы, не утверждение их наличия до начала. Если аналогичный файл уже существует по REPO_MAP, использовать его и указать mapping, не создавать дубль. Все пути относятся к корню проекта.

MVP: только личный бот, Telegram Mini App, четыре формата, full/viewer, семейные лайки. Без AI, групп, платежей и реализации будущих платформ. Новые семейные данные — только synthetic fixtures до приёмки закрытого пилота.

## Потребляемые и производимые интерфейсы
Потребляет семейный API 01, оболочку 06 и доступные действия HostBridge; не зависит от live feed 07. Не создаёт membership до явного подтверждения приглашения и не обходит backend guards.

## Порядок выполнения
1. Создать onboarding поD15: имя ребёнка, необязательная дата рождения, timezone и отдельное согласие без заранее установленной галочки. Приглашение не показывает медиа семьи до принятия.
2. Страница Семья показывает участников, роли, владельца и объём архива. Технические Telegram IDs и токены не показываются.
3. Owner открывает sheet приглашения. Роль по умолчанию — Просмотр. Обе роли имеют конкретные пояснения. Ссылка одноразовая на72часа; отправка вручную или копирование, без автоматической рассылки контактам.
4. Экран принятия показывает семью и права. Отдельные состояния для истечения, отзыва, использования и участия в другой семье.
5. Изменение роли и удаление участника доступны owner с подтверждением. Full без владения управляет контентом, а не составом семьи.
6. Выход из семьи отличается от завершения сессии. После отзыва доступа очистить кэш. Контакт поддержки берётся из конфигурации, не выдумывается.
7. Пояснить отдельное хранение копии и возможность скачивания оригинала без неподтверждённых обещаний.

## Обязательные сценарии проверки
F08.1 Приглашённый viewer видит общую ленту. F08.2 Открытие ссылки не присоединяет автоматически. F08.3 Начальная роль — viewer. F08.4 Подмена role в клиентском URL не повышает права. F08.5 Owner нельзя удалить или понизить. F08.6 Длинные Unicode-имена корректно переносятся. F08.7 Отозванный участник не получает медиа. F08.8 При отсутствии share работает копирование. F08.9 Дата рождения действительно необязательна, timezone валиден.

## Проверочный цикл каждого изменения
- [ ] Найти существующие границы и перечислить затронутые файлы до редактирования.
- [ ] Для каждого сценария выше написать или уточнить тест на ближайшем подходящем уровне.
- [ ] Запустить новый тест до реализации и убедиться, что падение относится к нужному поведению, а не к случайной ошибке окружения.
- [ ] Реализовать минимальное изменение в указанном модуле, не менять контракт без согласования его потребителей.
- [ ] Запустить тот же тест, затем связанные проверки из плана области влияния.
- [ ] Проверить diff и выполнить самостоятельный review. При назначенном Sol review получить отдельный проход без опоры только на отчёт исполнителя.
- [ ] Записать команды, результаты и ограничения в отчёт по `../review/BLOCK_REPORT.md`.
- [ ] Передать владельцу результат и остановиться до следующего блока. Commit — в своей ветке, без автоматического merge/deploy.

## Команды проверки
Новые тестовые файлы с указанными именами создаёт этот блок. Фильтр должен реально находить тесты: ноль найденных тестов не является успехом. Если выбранный Vibe использует другую эквивалентную команду, обновить REPO_MAP/verification-map и привести фактический запуск.
```bash
bun run test:webapp
bun run --cwd webapp e2e -- family.spec.ts
bun run test:backend:integration -- src/modules/families/family-access.integration.test.ts
```

## Что показать владельцу
Один тестовый организатор создаёт семью и приглашает двух людей с разными ролями. Viewer ставит сердечко и не получает кнопок изменения.

## Критерий готовности
Приглашения и управление участниками работают без редактирования БД; операционный пилотный допуск нужен только первоначальному организатору.

## Стоп-условия
Не добавлять дерево родства, телефоны, публичный поиск семей или оплату приглашений.

Невозможность запустить обязательный тест отмечается `BLOCKED` с причиной; не заменять его проверкой синтаксиса. Успех в локальной БД не доказывает готовность production-конфигурации.
