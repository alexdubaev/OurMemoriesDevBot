Этот файл конкретизирует [T-09.5.1.md](T-09.5.1.md), не меняет frozen UI reference. Две исходные копии общего ТЗ различаются только HTML-разметкой первых строк: требования и критерии идентичны. Незакоммиченный файл в основном checkout оставлен нетронутым. В `main` после исходного B0 появились только правила агентов (#83–84), production schema/contracts/code не изменились. Старые single-family и pilot-admission положения `00_START_HERE.md`, `03_DATA_API.md` и `TASK_INDEX.md` замещаются только в явно описанном здесь scope поздним решением владельца; до активации старое поведение сохраняется.

## Проверенная основа и границы

- `FamilyMember` уже имеет PK `(family_id,user_id)`; отдельный partial unique `family_members_one_active_family_per_user_key` на `user_id` запрещает второе активное членство. `Family.ownerUserId` только индексирован; существующие FK и триггеры требуют активного full-владельца и отзывают доступ при retirement. Это расширяется, не заменяется вторым источником семей.
- `GET /api/v1/me` имеет strict DTO `{user,activeFamily,limits:{activeFamiliesMaximum:1}}`, а `getMe` выбирает `findFirst`. `createFamily` требует pilot admission и отсутствия любого членства; `acceptInvite` отвергает членство в другой семье. Новые ответы нельзя вставить в старый DTO. Existing `IdempotencyRecord` защищает создание; invite token блокируется `FOR UPDATE`, одноразовый и связан с конкретной семьёй.
- `Memory.createdSequence` — выделенная sequence, `occurredAt` — дата события; ни одно поле не определяет порядок commit первой публикации. API и source publisher сохраняют разные writer-пути. MAX task/image/voice/video и Telegram ingress сейчас исходят из одного членства; их B3 должен подготовить **до** включения нескольких семей. Явный webapp upload уже несёт `familyId`.
- B0 не изменяет backend, schema, contracts, миграции, webapp, CI и production. B1 получает только совместимое расширение и закрытый gate. B2 реализует серверные членства, B3 — выбор цели бота, B4 — unread, B5–B6 — UI, B7 — контролируемое включение. Ни один блок не включает второй membership в production сам по себе.

## Решение 1 — HTTP API, DTO, ошибки

**Recommended.** Сохранить `GET /api/v1/me` и его 0/1-member ответ без новых полей; при 2+ действующих членствах отвечать `409 CONFLICT` с безопасным сообщением об обновлении приложения, без `activeFamily`. `CONFLICT` уже существует и точнее, чем `ALREADY_IN_FAMILY`: последнее означает отказ операции создания/вступления, а не результат чтения. Новый отдельный `GET /api/v1/me/families` возвращает strict `version:1` DTO. Не менять `/api/v1/auth/me`. Explicit-family маршруты остаются под их ACL. Новый endpoint не делает старый клиент способным работать с несколькими семьями; до B7 проверить кэшированную PWA и предусмотреть понятное обновление клиента.

| Метод и путь | Request | Успешный ответ / права |

| `GET /api/v1/me/families` | query `limit` (default 20, max 50), opaque `cursor?`; body нет | 200: свои действующие членства только по сессии, своя active семья первой, затем Unicode-normalized name + `familyId`; 401 без сессии. Данные карточек и counters читаются совместно без N+1 по семьям. |

Успешный повтор тому же участнику → прежний результат; consumed другим → 409 `INVITE_USED`; expired/revoked → прежние 410 `INVITE_EXPIRED`/`INVITE_REVOKED`. |

В той же транзакции перед записью **каждый** ID должен принадлежать этой семье и быть `status=published`, `deletedAt=null`; processing/failed, неверный, недоступный или удалённый ID → 404 `NOT_FOUND` для всего пакета без частичной записи. Повтор действительного пакета → 204; stale epoch → 409 `VERSION_CONFLICT`. |

`GET /me/families` response: `{version:1, ownFamilyId:uuid|null, ownFamilyStatus:'active'|'deleting'|null, canCreateOwnFamily:boolean, items:FamilySummary[], nextCursor:string|null}`. `ownFamilyId` включает неудалённую семью в `deleting`, но `items` содержит только доступные active семьи. `canCreateOwnFamily` сервер вычисляет из gate, действующей сессии, собственной неудалённой семьи и применимой policy; это UI hint, не разрешение для POST. `FamilySummary`: `{familyId,name,displaySubtitle:string|null,childAvatarMediaId:uuid|null,isOwner,role:'full'|'viewer',setupStatus:'needs_child'|'ready',capabilities,unreadCount:integer|null,unreadState:'ready'|'unavailable'|'not_enabled',membershipEpoch:positive integer}`. `capabilities` — server-derived booleans `canCreateInvite`, `canManageMembers`, `canEditChild`, `canPublishNote`, `canPublishPhoto`, `canPublishVoice`, `canPublishVideo`, `canUploadChildAvatar`; video учитывает текущий provider/host, при отсутствии доказанной policy возвращает `false`. Пока unread не включён: `null/not_enabled`. Ошибка counters: `null/unavailable`, а не ложный ноль; прочие поля списка доступны. `membershipEpoch` серверный version token для precondition seen, не полномочие. Числа JSON bounded safe integers; ordinal в публичный DTO не выводится.

Клиент вправе передать только фильтры/курсор/limit, прежние данные create/invite, IDs увиденных карточек и **эхо** `expectedMembershipEpoch`. Сервер не принимает `userId`, `role`, `isOwner`, `familyId` внутри body seen, `joinedAt`, baseline, publication ordinal, count, `seenAt`, source target или capability как источник прав. Path `familyId` всегда сверяется с членством сессии. Своя/чужая недоступная семья и чужая Memory → одинаковое 404 `NOT_FOUND`, не 403 с раскрытием существования. 403 `ROLE_FORBIDDEN` только когда членство установлено, но действие запрещено ролью; `viewer` имеет право чтения/seen. 401 `SESSION_REQUIRED` без сессии; malformed body/cursor/mismatched signed cursor context → 422 `INVALID_INPUT`; истёкший epoch уже принятого cursor → 409 `VERSION_CONFLICT`; rate limit → 429 `RATE_LIMITED`. Повтор GET безопасен; повтор seen безопасен; cursor списка подписывает состав/order snapshot; при смене имени/членств сервер отвечает 409 `VERSION_CONFLICT` и клиент начинает pagination заново, не пропуская карточки. Бот-выбор B3 идёт через существующий authenticated provider callback/adapter, отдельный публичный HTTP endpoint B0 не предписывает.

**Alternative considered:** расширить strict `/me` массивом либо ввести новую `/api/v2` для всего приложения. Первое ломает старый клиент; второе размножает контракты и маршруты ради одного нового projection. Отдельные endpoints для counters и unread создают дополнительный round-trip без потребности MVP. **Compatibility:** старые 0/1 ответы и existing create/invite DTO сохраняются; cached single-family клиент получает явный 409 вместо произвольной семьи. **Migration/data:** API само не переносит данные. **ACL:** все IDs и capabilities серверные, existing family-scoped access сохраняется. **Concurrency/retry:** idempotency key и epoch/cursor precondition предотвращают повторную запись/смешение семей. **Rollback/recovery:** после второго membership старый runtime не разворачивать; gate `off` запрещает новые несовместимые записи, но новый read path и явный legacy 409 остаются.

## Решение 2 — публикация, вступление и сериализация

**Recommended.** Источник истины — PostgreSQL `Family`, `FamilyMember`, `Memory`, `IdempotencyRecord`/provider source и таблица seen; отдельного notification log/Redis нет. Новое событие для unread — **первый commit**, после которого данная `Memory` имеет `status=published` и `deletedAt=null` и доступна в feed. Для note это вставка сразу published, для media — переход из processing/failed; attachment, edit, like, retry source и повторный callback не являются новой публикацией. `occurredAt`, wall-clock и `createdSequence` не используются как граница новизны.

У семьи есть `publicationOrdinal` (начально 0) и durable `unreadTrackingActivatedAt`. У Memory nullable `firstPublishedOrdinal`; у member `membershipEpoch` (начально 1) и nullable `unreadBaselineOrdinal`. **После активации** каждый writer первой публикации в одной транзакции берёт `SELECT families ... FOR UPDATE`, повторно проверяет ACL/source identity, увеличивает ordinal и записывает его на Memory одновременно с published. При неуспехе транзакции ни Memory, ни ordinal не подтверждены. Повтор уже published не увеличивает ordinal. B4 ставит DB guard: когда tracking активен, новая вставка/переход в published без ordinal отвергается; старые published с null можно редактировать, не присваивая им новый ordinal. Это закрывает обход забытым writer-путём и не превращает count в best-effort событие.

При вступлении/rejoin B2 сериализует изменения членства по `users` row `FOR UPDATE` (create/accept для одного actor); после проверки token/gate/own-family ограничения берёт `families` row `FOR UPDATE`. Если tracking уже активен, baseline нового периода равен committed `publicationOrdinal` в той же транзакции. Rejoin увеличивает epoch и обновляет baseline; прежние seen другой epoch не учитываются. Первое вступление до активации оставляет baseline null. При B7-активации lock семьи отделяет все до/после публикации/вступления. Для уже активного участника null baseline трактуется как 0, поскольку **весь старый архив имеет null `firstPublishedOrdinal`**; новые записи получают ordinal от 1. Не нужна отдельная операция на каждого прежнего участника. `version` членства сохраняет назначение optimistic role/profile version и не подменяет epoch. B4 проверяет опубликованный статус каждого ID и текущую epoch в той же транзакции, которая вставляет seen, иначе pending Memory могла бы быть отмечена до первой публикации и ошибочно исчезнуть из будущего unread.

Порядок commit под общим family row lock решает race publish vs join/activation: если publish раньше join — baseline включает его, если позже — запись новая; при включении старая публикация без ordinal остаётся архивом, следующая получает ordinal. Два параллельных create с разными ключами дополнительно арбитрирует partial unique своей семьи; разные invite accept для одного actor сериализуются user lock, token остаётся locked; одна строка membership на пару обеспечивает уникальность. Для удаления/отзыва целевой семьи B2–B4 повторно проверяют live ACL перед publish/seen; старый batch с прежней epoch отвергается. Source family+child фиксируются атомарно один раз до acquisition; retry/restart не вправе сменить цель. Локальный порядок lock в совмещённых операциях: actor user → target family → source/membership rows, кроме уже начатых provider-specific source locks; B3 обязан проверить и унифицировать порядок, чтобы не создать цикл deadlock. Никакого advisory/distributed lock в MVP.

**Alternative considered:** sequence/timestamp watermark, вычисление по `createdSequence`, advisory lock, глобальная очередь или in-memory событие. Они не дают подтверждённого порядка commit на всех writer-путях либо добавляют лишнюю инфраструктуру. **Compatibility:** пока все writers не обновлены, tracking выключен; существующая single-family публикация работает. **Migration/data:** additive поля и индексы, без переноса медиа/семей. **ACL:** scope и разрешение на тип проверяются в целевой семье до commit; viewer не становится publisher. **Concurrency/idempotency:** общий row lock и source uniqueness делают first publication единственной; join/rejoin и activation дают однозначную границу. **Rollback/recovery:** после активации старый writer, не пишущий ordinal, не запускать; DB guard предотвращает потерю события. При ошибке выключить новые multi-family изменения и исправить writer вперёд, не выбирать произвольную семью и не откатывать схему поверх новых членств.

## Решение 3 — миграция, архив, восстановление

**Recommended.** B1 — **expand-only** новая миграция: preflight на дубли неудалённых семей одного owner; partial unique `families(owner_user_id) WHERE status <> 'deleted'`; оставить старый unique активного членства; добавить совместимые поля/counter/indexes и таблицу seen с FK на `(family_id,user_id)` и `(memory_id,family_id)`, ключом `(family_id,user_id,membership_epoch,memory_id)`. Не редактировать исторические SQL, `pilot_admissions`, media, children или пользовательские темы. Не запускать data backfill в B1.

**Массовый backfill опубликованного архива не нужен.** У ранее published Memory `firstPublishedOrdinal=null` навсегда означает «до учёта»; у старых активных членов `unreadBaselineOrdinal=null` означает 0 только после включения tracking семьи. B4 обновляет оба publisher-пути и добавляет guard, прогоняет synthetic проверки; B7 отдельно включает tracking **по семье** короткой идемпотентной транзакцией с `families FOR UPDATE`, выставляя `unreadTrackingActivatedAt` один раз. Повтор activation читает уже заданную границу и ничего не сбрасывает. Ни один existing Memory не сканируется и не переписывается синхронно. Для вступившего после activation baseline записывается на момент join, включая текущий ordinal. Удаление/редактирование старого архива не делает его новым. Никакой пользовательский count не показывать `ready`, пока семья не активирована и все writers/потребители не проверены.

Частичный успех между семьями допустим только как **контролируемое состояние активации**: каждую семью отмечают отдельно, уже активированную не переинициализируют, остальные остаются `not_enabled`; общий UX rollout и multi-family gate `on` включать лишь после проверки всех целевых семей. Ошибка одной транзакции не оставляет половины ordinal/baseline внутри семьи. Resume повторяет только неактивированные семьи. Это production data action B7 и требует отдельного назначения владельца; B0/B1 никаких production данных не меняют. При нарушении guard/несогласованном ordinal остановить активацию и расследовать конкретные записи/source; не выдавать ноль и не «восстанавливать» порядок по `occurredAt`. Восстановление production backup может удалить новые записи и отдельно согласуется.

**Alternative considered:** SQL/долгий app job, присваивающий всем старым Memory ordinal, и массовое обновление всех members. Это создаёт блокировки/стоимость и не улучшает требование «старый архив не новый». **Compatibility:** nullable поля не требуют немедленного обновления старого runtime до активации. **Migration/data:** один additive B1 migration; снятие старого member unique только B2 вместе с готовым server guard и безопасной выкладкой; позднее B4 DB guard. **ACL:** FK seen связывают ту же семью, application ACL обязателен; historical rows не раскрываются. **Concurrency/idempotency:** activation под тем же row lock, повтор без reset, per-family commit. **Rollback/recovery:** B1 schema можно оставить неиспользуемой; после второй membership или activation требуется forward-fix/совместимый runtime, не восстановление старого индекса и не удаление «лишних» данных.

## Решение 4 — необходимые лимиты

**Recommended.** Не вводить произвольный максимум чужих членств/общих семей: три семьи бабушки — пример, а прежние «до 10 семей/участников» в `00_START_HERE.md` — размер закрытого пилота, не действующий DB/API quota. Открытое создание не должно требовать ручного допуска; бюджет/ёмкость контролируются уже имеющимися rate limits, media квотами и мониторингом до расширения пилота. На одного owner — **одна** неудалённая своя семья, DB partial unique + B2 guard, при превышении `409 ALREADY_IN_FAMILY`. На пару user/family — одно членство, существующий PK, повтор same invite безопасен. Не делать новую произвольную квоту участников без отдельного решения о вместимости; существующие права и хранение не ослаблять.

| Ограничение | Зачем / где enforced | Ответ / этап |
|---|---|---|
| `GET /me/families` page default 20, max 50; `GET memories` уже default 20, max 50 | Ограниченный ответ и работа счётчиков; strict query schema + indexed keyset/cursor | Некорректный limit/cursor → 422 `INVALID_INPUT`; MVP B1/B4. |
| Seen batch 1..50 submitted IDs, один family/epoch | Ограничить транзакцию и повторы observer; strict schema, дедупликация внутри и `ON CONFLICT DO NOTHING` | Пустой/51-й ID → 422 `INVALID_INPUT`; повторяющиеся IDs внутри допустимого пакета дедуплицируются. MVP B4/B6. |
| Bot pending choice 15 минут от source | Требование раздела 10.3; durable deadline в B3, provider availability проверяется заново | Истёкший callback не публикует, сообщает повторить отправку; provider transport использует имеющийся безопасный error/notice, не новый публичный API code. MVP B3. |
| Existing per-family media quota 2 GiB default, pending uploads 5 default, type/size caps | Сохраняют бюджет и storage safety; existing env/repository reservation/finalize | Текущий media transport возвращает 413 `FILE_TOO_LARGE` для quota/pending, 413/415 для размера/типа; без изменения в B1. |
| Existing HTTP limiter default 60/60s и provider retry/timeout bounds | Сейчас middleware назначен `/api/v1/families/*`, а create находится на корне `/api/v1/families`; B2 обязан применить тот же limiter к корню после проверки Hono matching. Existing adapters сохраняют свои bounds. | 429 `RATE_LIMITED` с действующей политикой; не добавлять B1-specific magic rate. Измерить нагрузку перед B7. |

**Alternative considered:** новый глобальный cap 10, cap чужих семей 3, Redis limiter/очередь и отдельные таймауты для каждой операции. Они не являются принятым продуктовым лимитом и могут скрыто вернуть ручной пилот. **Compatibility:** действующие ограничения media/rate остаются; новые page/batch пределы касаются только новых операций. **Migration/data:** одна собственная семья обеспечивается новым индексом, остальные лимиты без миграции. **ACL:** лимиты не заменяют проверку членства. **Concurrency/idempotency:** unique/index, ограниченный batch и существующая reservation/idempotency инфраструктура. **Rollback/recovery:** gate `off` останавливает новые multi-family записи, существующие семьи сохраняются; capacity incident решается штатным rate/quota/операционным контролем, не удалением данных.

## B1 после принятия B0

**Base и владение:** новый актуальный `origin/main` после принятого B0; один назначенный интегратор владеет schema, новой migration, shared contracts, family route/composition и env.
