## Зафиксированные решения

### Данные и ограничения

1. **Своя семья.** Новая частичная уникальность PostgreSQL на `families(owner_user_id) WHERE status <> 'deleted'` удерживает слот в `active` и `deleting` и атомарно разрешает гонку двух устройств с разными idempotency keys. Предварительная проверка нужна для понятного ответа, индекс — окончательный арбитр. Проверить перед миграцией, что текущие данные не нарушают индекс. Различать конфликт own-family, membership и idempotency; не перехватывать любую unique-ошибку как один код. Исторические семьи/удаления не очищать.
2. **Членства.** Сохранить одну строку и PK `(family_id,user_id)`; снять только старый partial unique по `user_id`. Rejoin по новому действующему приглашению обновляет эту строку, повышает отдельный `membership_epoch`, задаёт новый `joinedAt` и unread baseline, а прежние seen строки другой эпохи не действуют. `version` остаётся оптимистической версией роли/профиля, не epoch. Владелец остаётся full member и связан с Family существующими FK/trigger.
3. **Публикационная граница.** Для unread в B1 добавить nullable метаданные `families.publication_ordinal` (счётчик), `memories.first_published_ordinal`, `family_members.unread_baseline_ordinal`, `family_members.membership_epoch`; отдельную таблицу seen с ключом `(family_id,user_id,membership_epoch,memory_id)`. Первое присвоение ordinal, вступление/rejoin и начальная активация существующих участников в B4 сериализуются одним транзакционным family lock и записывают/читают ordinal в БД. Публикация получает ordinal только один раз при **первой** видимости `published`; retry/late attachment/edit его не меняют. `occurredAt`, wall clock и текущий `createdSequence` для этой границы не использовать. B1 оставляет поля nullable/неактивными, пока все writer-пути не готовы; B4 проводит backfill старого архива и фиксирует baseline один раз при контролируемой активации. После активации записи без ordinal должны вызывать диагностику/восстановление, а не молча исчезать из счётчика. Join и publish под тем же lock дают однозначное `>` baseline.
4. **Seen.** Считать только доступные `Memory` со статусом `published`, без `deletedAt`, чужого автора и `first_published_ordinal > baseline`. Seen — вставка с `ON CONFLICT DO NOTHING` в текущую epoch после ACL и принадлежности Memory семье; viewer имеет право отмечать. Bounded batch, фиксированные family/user/epoch; поздняя отметка старой epoch отклоняется. Счётчик вычисляется сервером по indexed Memory/seen, не `count--` в UI. Ошибка счётчика даёт `null/unknown`, не ноль. Опубликованное позже старой датой считается новым; свои, attachment, like, edit и retry не прибавляют. Удаление исключает строку.

### Контракты и включение

5. **Новый семейный стартовый контракт:** отдельный `GET /api/v1/me/families`, strict versioned DTO `{ version: 1, canCreateOwnFamily, ownFamilyId: uuid|null, families: [...] }`. Элемент: `familyId`, `name`, `displaySubtitle: string|null`, `childAvatarMediaId: uuid|null`, `isOwner`, `role: full|viewer`, `setupStatus: needs_child|ready`, `capabilities: { canView, canCreateInvite, canManageMembers, canEditChild, canPublishNote, canPublishPhoto, canPublishVoice, canPublishVideo, canUploadChildAvatar }`, `unreadCount: integer|null` и `unreadState: ready|unavailable|not_enabled`. `canPublishVideo` проверяет фактическую MAX/provider возможность вместе с family policy; capability не обещает успех текущего upload при потере сети/квоты. Сортировка: своя, затем name+familyId; данные карточки берутся только из доступной семьи. Список может работать при сбое unread. До B4 значения unread `null/not_enabled`.
6. **Старые клиенты.** `/api/v1/me` и его strict DTO оставить побайтно совместимыми для 0/1 membership. При 2+ active membership возвращать явный `409 multi_family_client_update_required` без `activeFamily`, а не `findFirst`; новый клиент использует отдельный endpoint. Старый клиент может показать ошибку/обновление, но не выбрать чужую первую семью. Старые explicit-family API продолжают проверять ACL. Контрактная fixture для 0/1/2 membership и кэшированной PWA обязательна до включения. Не менять SW lifecycle без отдельного доказанного требования.
7. **Activation gate.** Минимальный server config `MULTI_FAMILY_ACTIVATION=off|on`, default `off`, одна конфигурация для API и workers. **В B1 старый DB unique одной активной семьи остаётся на месте**: расширение схемы само не открывает второе членство. B2 может снять его новой миграцией лишь вместе с транзакционной сериализацией create/accept по строке пользователя (`FOR UPDATE` до проверки членств) и проверкой gate. При `off` сохраняются текущие результаты create/accept (включая pilot admission), второе членство и открытое создание недоступны даже при двух конкурентных приглашениях. Деплой B2 schema при старом writer runtime без такой защиты запрещён; B7 проверяет порядок выкладки и отсутствие старых writer-процессов. Включить `on` только в B7 после готовности ботов, нового UI, unread и проверки old clients. После появления нескольких членств возврат `off` запрещает **новые** multi-family изменения, но новый runtime продолжает обслуживать существующие несколько членств через family-scoped API/list; `/me` остаётся явным 409. Параметр не является product pilot admission. UI capability отражает текущий gate.

### Публикация и лента

8. **Боты.** Для каждого входящего source и конкретного `note/photo/voice/video` получить допустимые активные семьи по действующему членству, готовому child и реальной type/provider policy. 0 → отказ без публикации; 1 → автопривязка; 2+ → durable pending choice этой отправки (начально 15 минут), подписанный/неугадываемый callback связан с actor+source. Viewer семьи не создают неоднозначности. MAX task/image/voice/video и поддерживаемый Telegram ingress должны использовать один смысл selector; существующие album/caption/reply pathways сохраняют свою source-связь. Явный direct upload не спрашивает повторно.
9. **Неизменяемая цель.** Source/pending operation получает `familyId+childId` только один раз атомарным compare-and-set до acquisition/upload. Provider source identity, upload session и planned memory/media IDs привязаны к тому же source/family; повтор callback, worker restart и навигация не могут переписать цель. До publish снова проверить членство и type permission. Отзыв → отказ, без перенаправления. Caption/reply ищет исходный source/memory по сохранённой паре, не по текущему viewer контексту; две ожидающие отправки независимы.
10. **Unread pagination.** Отдельный cursor version для unread, HMAC+expiry, привязан к `userId`, `familyId`, `membership_epoch`, `kind/childId`, режиму unread, `snapshotOrdinal` и keyset `(occurredAt,id)`. Первый запрос берёт committed family ordinal после lock; следующие страницы ограничены `first_published_ordinal <= snapshotOrdinal`, `> baseline`, unseen на момент каждого запроса, и идут существующим `occurredAt DESC,id DESC` keyset. Seen/deleted между страницами лишь убирают строки, offset-пропусков нет; новые публикации ждут refresh. Уже отрисованные seen карточки остаются до явного обновления, хотя серверный count падает. Cursor чужого user/family/epoch/filter отклоняется. Текущий обычный feed cursor v2 не переписывать этим решением.
11. **Recovery.** B1 expand-only и выключенный gate можно откатить лишь после проверки совместимости старого runtime со схемой. После первой второй membership старый runtime уже небезопасен: выключить новые записи, оставить новый read/scope путь, выполнить forward-fix или заранее проверенный совместимый релиз. Не восстанавливать старый unique поверх данных, не удалять членства. При ошибке unread backfill/ordinal остановить активацию и восстановить метаданные из published Memory под тем же family lock; backup restore production — отдельное решение владельца с риском потери новых записей.

## B1 — точное предложение следующего назначения (B1 не начат)

**Base:** только принятый после B0 актуальный `origin/main`; интегратор единолично владеет schema, migrations, contracts, route/composition и config. **Allowed paths:** `backend/prisma/schema.prisma`; новая папка `backend/prisma/migrations/<новый_timestamp>_t0951_multifamily_foundation/migration.sql`; `packages/contracts/src/families.ts` (новый DTO/exports); `backend/src/modules/families/{application,transport}/` только для отдельного read contract и server activation guard; `backend/src/env.ts`, `.env.example` только для gate; целевые `backend/src/modules/families/*.test.ts`, `backend/src/env.test.ts`, `packages/contracts/src/*.test.ts`, при необходимости новые focused migration/contract tests. Список конкретных файлов уточнить перед началом B1 по принятым контрактам; общий файл изменяет один назначенный владелец.

**Forbidden paths:** `docs/memoly-final-functional-state-pack.html`; `archive/`; существующие миграции; `backend/src/modules/{max,telegram,media,memories}/` (реализация B3/B4); `webapp/src/` (B5/B6); CI/deploy/production, lockfile/dependencies, PR #77. Никаких apply migration к production, merge или deploy в B1.

**Миграция:** preflight данных; новый partial unique own-family; **старый one-active-membership unique пока сохранить**; новые nullable/compatible поля и seen table/indexes/FK, без backfill или включения unread; не изменять historical `pilot_admissions`, темы и другие применённые миграции. Индекс и FK проверить на существующих данных. B1 не делает публикационный ordinal обязательным для старых writers. Снятие старого индекса планируется в B2 вместе с server guard, затем B7 контролирует фактическую активацию.

**Контракты:** новый `GET /me/families` DTO с null unread; старый `/me` без добавления полей и с явным 409 при неоднозначности; activation default off. Новые пути создания/accept с несколькими членствами пока не включать. Не обещать capabilities без фактической policy; если video policy требует отдельной проверки в B2/B3, вернуть `false` до её реализации.

**Тесты и критерии приёмки:** миграция пустой и существующей synthetic БД, сохранение users/families/children/media/roles; два конкурентных create разных keys дают одну собственную семью по DB индексу; старый one-active индекс реально действует; contract/service fixtures с двумя членствами не выбирают первую и возвращают явный 409 на legacy `/me`; новый strict DTO parse; default off и некорректное значение gate fail closed; существующие family ACL/owner triggers и idempotency не регрессируют. Epoch/seen schema проверяется на синтетических данных; live rejoin и unread semantics проверяются в B2/B4. Результаты фиксировать с числами/exit codes. До B3/B4/B5/B6/B7 gate остаётся off.
