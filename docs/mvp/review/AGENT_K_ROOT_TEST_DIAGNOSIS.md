# Agent K: root test runner diagnosis

`bun run test` runs infra → contracts → backend unit → backend integration → webapp → website. The backend integration runner (`backend/scripts/test-integration.mjs`) chooses a random, isolated Docker Compose project per run. Compose creates a fresh default network and a test PostgreSQL container/volume, applies migrations, executes each integration file sequentially, then removes its own resources.

On this host, a default run stops at Docker network creation with `all predefined address pools have been fully subnetted` (exit 1). Docker lists existing networks occupying its default 172.17–172.31 `/16` and 192.168 `/20` pools. Agent K did not remove or alter those other projects. The runner's subsequent failed attempt to remove the never-created network is a secondary cleanup message. No test failure was hidden or converted to success.

For diagnosis, Agent K created only `agent-k-acceptance-test` on `10.251.42.0/24` and `agent-k-acceptance-postgres` on loopback port 56432, with separate disposable databases. With `TEST_SKIP_DOCKER=1` and a `*_test` URL, the **unchanged** root runner applied migrations and completed with exit 0. The `users` integration file completed all 14/14 tests and the root sequence reached website tests. This clean, isolated run did not reproduce Agent J's reported stall after `users` 12/14. The previous stall has no verified code-level cause, so no timeout or production test-runner behavior was changed.

A later standalone integration run against the same database used by browser E2E failed at `prisma.user.deleteMany()` because E2E families retained a foreign key to their owner. That is a repeat-run database isolation error in the manual `TEST_SKIP_DOCKER` workflow, not a failing assertion in the application. A new disposable database (`web_app_demo_k2_test`) made `bun run test:backend:integration` complete with exit 0. The normal Compose runner already provisions a fresh test volume; operators using `TEST_SKIP_DOCKER=1` must provide a clean, dedicated database per suite.

One later clean root run hit a 60-second timeout in `MAX durable capture > cleanup-first row locking makes publication fail without a Memory`. Its test process then remained pending until interrupted, although PostgreSQL showed no active lock waiter. The same test passed alone (1/1, 229 ms), its full file passed (40/40, 7.56 s), and another clean root run completed (1213/1213, exit 0). The first clean root run also completed. This is an intermittent test-runner/async-cleanup risk, not a demonstrated product failure or a reproducible database lock. No timeout was increased and the failure is retained in the local log; further investigation is warranted if it recurs in CI.

**Acceptance status:** default `bun run test` is blocked by the shared Docker host address pool; isolated `bun run test` completed twice with exit 0, with one intervening intermittent timeout/hang as described above. The prerequisite for a default run is free Docker pool capacity or an approved, isolated explicit-subnet test-network configuration. Agent K will remove only its own temporary container and network after final verification.
