# Хранение, безопасность и честные обещания

## 1. Решение для основного MVP
**Telegram — канал получения. PostgreSQL — записи и семейные права. Приватное S3-совместимое хранилище — копии файлов.** Оригиналы держим независимо от file_id. Для локальной разработки использовать существующий изолированный драйвер Vibe; для пилота — private bucket, не временный filesystem контейнера.

Это сознательный выбор спецификации ради воспроизведения медиа, выгрузки и будущих независимых клиентов. Провайдер и регион не выбраны, покупку не выполнять без владельца. Во время code-only разработки реальные облачные credentials не нужны. [V5]

## 2. Можно ли обойтись хранением в Telegram
Технически bot получает file_id, который позволяет повторно отправлять файл. Но для интерфейса Mini App нужно отдельное безопасное получение bytes; ссылка getFile содержит bot token и не может попасть в браузер. Облачный getFile ограничивает размер, собственный proxy несёт трафик/нагрузку. Идентификатор привязан к конкретному боту. [T1,T3]

Дополнительно условия Telegram 6.3 не гарантируют постоянную доступность данных; 5.2(e) ограничивает использование Bot Platform как основы внешних облачных хранилищ. Это не автоматическое заключение о запрете конкретного дневника, но оснований обещать бесплатный бессрочный backend нет. [T4]

**В этом комплекте Telegram-only не реализуется.** Если владелец позже выберет такой опыт, нужен отдельный disposable demo на неуникальных тестовых файлах, без обещания архива и с проверкой условий. Не добавлять сейчас вторую полноценную ветку хранения/флаг «потом выберем». Сам порт хранения остаётся заменяемым. Экономить можно на небольшом лимите пилота, а не на ложной отметке «сохранено».

## 3. Нормативные лимиты пилота
| Параметр | Значение |
|---|---:|
| Пилотные семьи / участники | 10 / 10 в семье |
| Оригиналы на семью | 2 147 483 648 bytes (2 ГиБ) |
| Фото | ≤20 000 000 bytes; ≤40 megapixels; 1–10 в записи |
| Голос / аудио | ≤20 000 000 bytes; ≤600 секунд |
| Видео через bot cloud getFile | ≤20 000 000 bytes |
| Видео напрямую из Mini App | ≤100 000 000 bytes; ≤180 секунд; ≤4K исходник |
| Note/body | ≤8 000 Unicode code points |
| Одновременное кодирование | 1 на worker в первом профиле |
| FFmpeg job deadline | 10 минут с heartbeat и hard-kill child process |
| Максимум pending uploads семьи | 5 |
| Upload reservation / signed PUT | 15 минут / 5 минут |
| Неуспешный temporary upload | удалить в течение 24 часов |

Лимиты — наши продуктовые решения, не гарантии сторонних платформ. При пересмотре лимита меняются серверная policy, API limits DTO, UI и тесты. Квота UI считает оригиналы; derivatives/backup учитываются внутренними метриками, чтобы не вводить пользователя в заблуждение.

## 4. Приём и производные
Signed upload-ticket выдаётся после `requireFull` и атомарного резервирования ожидаемых bytes. Key генерирует backend, без имени ребёнка, Telegram ID и email. Повтор путём перезаписи запрещён: новый upload получает новый key. Finalize проверяет владельца/семью/актуальные права, размер фактического объекта, сигнатуру и декодирование. MIME из браузера или Telegram — не доказательство формата.

Оригинал никогда не подменять оптимизированной копией. JPEG/PNG/WebP/HEIC/HEIF → нормализованная display WebP ≤1600 px по длинной стороне + preview ≤720 px, orientation исправлена, metadata location удалена из производных. Оригинал может содержать EXIF, и это честно указано в политике; он приватен. HEIC нужно проверять реальным sample в deployment-бинарнике, не только наличием MIME в коде.

Видео MP4/MOV H.264/HEVC принимается после ffprobe. Playback: MP4 H.264, yuv420p, AAC если есть audio, max720p, faststart, без случайного upscale. Если исходник уже совместим, допустим remux, но original неизменен. Voice → M4A/AAC, исходный OGG/Opus сохраняется. Preview waveform состоит из 48 измеренных амплитуд 0..1; при отсутствии данных показывается обычная полоса прогресса, не выдуманная волна.

FFmpeg и image decode выполняются без shell string interpolation, не под root, с ограничением CPU/RAM/disk/time; запрет сетевого доступа кодировщика, чтения вне job tmp и произвольных URL. Нужны обновления decoder binaries. Проверить лицензию конкретной сборки FFmpeg, а не объявлять весь её состав MIT.

Оригинал проверен → original_status=stored; соответствующая Memory публикуется. Rendition может быть pending: карточка не обещает проигрывание до ready. Неуспех preview не удаляет оригинал, есть повтор и скачивание исходника.

## 5. Выдача файлов
MVP выдаёт файлы через наш authenticated same-origin endpoint с проверкой active membership и published attachment на **каждый GET/HEAD/Range**. Backend потоково читает private storage; не загружает целое видео в RAM. Поддержка одного RFC byte range (206), HEAD, Content-Length, MIME, 416 на недопустимый диапазон; multi-range не нужен.

Не выдавать file_id, original_key, bot-token URL, credentials или публичные ссылки в DTO. API и private media имеют `Cache-Control: private, no-store`, прокси/CDN не кеширует их публично; `Referrer-Policy: no-referrer`. Скачивание original доступно участнику через тот же guard.

Подписанная загрузка в bucket не даёт доступа к другим объектам. После отзыва прав даже ранее созданный ticket не позволяет finalize/publish; объект позже очищается. Уже скачанные пользователем данные нельзя отозвать. Для будущего CDN короткие read tickets возможны отдельной задачей; сейчас они не нужны.

## 6. Авторизация и сессии
raw initData проверяется на сервере по официальному алгоритму, включая auth_date: максимум 5 минут, не более 30 секунд в будущем. `initDataUnsafe.user` не является подтверждением личности. Сравнение HMAC constant-time, обработка невалидных/повторяющихся параметров fail-closed. Bot ID/secret server only. [T2]

Использовать существующую схему сессий Vibe, согласовав Telegram exchange. Same-origin app/API под одним HTTPS host; secure HttpOnly cookies, CSRF/Origin checks на изменяющих запросах, refresh rotation. Auth token не в localStorage, URL или логах. Роль семьи читается из membership при запросе, а не доверяется старому JWT.

Replay: зафиксировать fingerprint initData на короткий TTL 5 минут атомарно с созданием сессии. Повтор с действующей той же сессией идемпотентен; повтор без неё не выдаёт новую сессию — предложить заново открыть Mini App. Существующий пользователь не теряет сессию только из-за устаревшего initData: работает refresh flow. Частые повторы, forged/future payload покрыты тестами.

Обязательная поддержка пилота: Telegram iOS/Android. Browser-only fixture login разрешён только development/test и в production отсутствует. При блокировке cookie в неподдерживаемом окружении — понятный экран открыть Mini App в мобильном Telegram; не включать незаметно незащищённый fallback. Дополнительные клиенты Telegram проверяются до включения в матрицу поддержки.

Webhook secret через `X-Telegram-Bot-Api-Secret-Token`, постоянное сравнение, лимит body. Ни одного запроса на Telegram OTP. Invite token хешируется, одноразовый consume под транзакцией; роль только серверная, не из query-параметра пользователя.

## 7. Изоляция и эксплуатационные права
Администратор инфраструктуры технически может иметь доступ к БД/хранилищу. В продукте не обещаем end-to-end encryption или что оператор физически не может прочитать данные. Пользовательского интерфейса «посмотреть все семьи» не создаём. Операционный доступ минимальный, журналируется.

Данные, DB volumes, job payload и резервные копии шифруются at rest; ключи хранятся отдельно от зашифрованных данных. Для S3 подтвердить поддерживаемое server-side encryption выбранного провайдера, для дисков — encryption управляемой инфраструктуры или проверяемая настройка. TLS снаружи, PostgreSQL не публичен. Секреты только env/secret store, не Git, PR, screenshots. [T4]

## 8. Удаление и сроки
Удаление записи сначала ставит deleted_at и прекращает выдачу, затем в той же транзакции enqueues список object IDs. Хранить references до подтверждения удаления каждого объекта; retries не теряют keys. Уборка orphan uploads и сверка private keys с БД выполняются ежедневно.

Нормализованное содержимое inbox удалить спустя 72 часа после обработки; обработанные source IDs/dedupe mapping без содержимого держать до удаления записи. После удаления оставить минимальный хешированный tombstone источника на30дней для защиты от повторной публикации; затем очистить. Raw content не хранится в этом tombstone. Pending CaptionRequest TTL10мин, удалить через24ч. Операционные логи без контента 14дней. Ready export ZIP зашифрован, private, expires72ч.

Оригиналы хранятся пока активен пилот/семья; нет «навсегда». После пользовательского удаления live-объекты удалить в пределах24ч при исправной инфраструктуре, инцидент обрабатывается оператором. Backup retention30дней; tombstone ledger сохраняет требования удаления, и перед возвратом восстановленной базы в работу повторно применяются tombstones. Нельзя утверждать мгновенное физическое уничтожение всех резервных копий.

## 9. Резервирование и выгрузка
До первой реальной семьи: daily DB backup + независимая копия private objects, не просто другая папка на том же диске. Контроль успеха, шифрование, 30дней retention, первая restore drill с проверкой хешей и прав. Целевые RPO24ч и RTO8ч — операционные цели пилота, не SLA.

Экспорт владельцу: ZIP с JSON manifest, заметками UTF-8, исходниками, датами, порядком и подписями; никакой обязательной зависимости от нашей БД для чтения текста. Source Telegram identifiers в export не нужны. ZIP создаётся фоново/операционной командой, исключает deleted rows, скачивание только после проверки owner. Другие члены могут сохранять видимые файлы по одному.

## 10. Допуск реальных семей
Нужны фактический оператор и контакт поддержки, опубликованная политика, описание Telegram/нашего хранения и сроков, добровольное согласие взрослых участников, проверка прав на размещаемые материалы, выбранный регион и проверка применимых требований к данным. Это технический перечень проверки, не готовое юридическое заключение. До заполнения operator/contact/domain поля остаются блокирующими условиями запуска, а не вымышленными реквизитами.
