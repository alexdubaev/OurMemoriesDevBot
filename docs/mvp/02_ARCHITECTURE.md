# Архитектура: независимое ядро, Telegram первым

## 1. База
Канонический продуктовый репозиторий — `alexdubaev/OurMemoriesDevBot`; HTTPS/SSH и правила remotes описаны в [REPOSITORY.md](REPOSITORY.md). `origin` продукта никогда не указывает на Vibe.

Использовать `di-sukharev/vibe`, ветку `master`; исследованный SHA `f2731e02547fb1118e233c99c47b4ec7c5fc8ba6`. До копирования проверить доступность именно этого коммита и актуальные security fixes, затем зафиксировать выбранный SHA в `UPSTREAM.md`. README и документация шаблона — полезные исходные инструкции, но не разрешение расширять согласованный продукт или создавать платные ресурсы.

Сохраняем Bun/Hono, Prisma/PostgreSQL, React/Vite, TanStack Query/Router/Form, Zod-контракты, существующие UI-примитивы. Не переносить UI в Next.js, не добавлять второй backend. Версии берём из выбранного lockfile и проверяем на этапе 00; PostgreSQL не понижаем относительно требований uuidv7 шаблона. [V1–V4]

## 2. Единицы ответственности
| Модуль | Владеет | Публичные действия |
|---|---|---|
| `auth` | Личности, сессии, Telegram exchange | authenticate, issueSession, revokeSession |
| `families` | Семьи, дети, membership, приглашения, пилотные лимиты | requireMember, requireFull, acceptInvite |
| `memories` | Записи, порядок, текст, likes | createNote, createMediaMemory, updateMemory, listMemories |
| `media` | Медиа-объекты, оригиналы, производные, квоты, доступ | reserveUpload, ingestTelegramFile, streamContent, deleteMedia |
| `telegram` | Inbox, mapping сообщений, подписи, replies, адаптер `@OurMemoriesDevBot` | acceptUpdate, processUpdate, sendReceipt |
| `privacy` | Выгрузка и удаление семьи, журнал выполнения | requestExport, requestErase, executeJob |

Общие технические средства: runtime, config, логирование, storage-port, outbox. Это не место для семейных разрешений или универсальной бизнес-логики. Глобальные таблицы Vibe users/admin не используются как права семьи.

## 3. Структура исходников
```text
backend/src/modules/{auth,families,memories,media,telegram,privacy}/
  index.ts                   # единственная внешняя граница модуля
  application/               # действия, политики, оркестрация
  domain/                    # только если есть чистые правила
  infrastructure/            # Prisma, Bot API, S3, FFmpeg
  transport/                 # Hono endpoints, проверка wire payload
backend/src/outbox/          # существующая надёжная очередь
backend/src/jobs.ts          # реестр заданий
backend/src/worker.ts        # исполнение, не бизнес-правила
packages/contracts/src/{families,memories,media,auth}.ts
webapp/src/features/{session,family,feed,memory,composer}/
  index.ts
  api.ts
  components/
  *.test.ts
webapp/src/platform/telegram/   # единственное место browser Telegram API
webapp/src/platform/{api,media}/
webapp/src/components/ui/       # повторно используемые низкоуровневые детали
webapp/src/styles/tokens.css
```

Существующие пути шаблона не переименовывать механически; при совпадающей ответственности расширить существующий feature, записать mapping в `REPO_MAP.md`. Внешние модули не читают Prisma-таблицы соседа напрямую. Синхронный вызов через публичный интерфейс предпочтительнее дополнительного HTTP внутри одного backend.

## 4. Зависимости
`telegram → families + memories + media` через явные порты. `memories → families` для разрешений и узкий `MediaCatalog` для проверки вложений. `media → families` через `FamilyAccess` и узкий `AttachmentAccess` от memories для чтения только опубликованных связей. Эти обратные возможности передаются при композиции, не импортируются циклически. `privacy` оркестрирует публичные удаления/экспорт, не обходит их прямыми удалениями строк.

Принцип: импорт SDK Telegram допустим только в telegram/auth Telegram adapter и webapp/platform/telegram. React-компоненты карточек не импортируют `Telegram.WebApp`, Hono, Prisma и SDK хранилища. Доменная запись не содержит обязательного `telegram_message_id`.

## 5. Как запись проходит систему
Telegram webhook проверяет секрет → минимальная проверка обновления → транзакция inbox + enqueue → HTTP 200. Worker определяет пользователя/семью и актуальные права → создаёт запись/импортирует файлы → подтверждает публикацию. Если БД недоступна до durable accept, не отвечать успехом.

Мини-апп использует те же действия приложения через API. Его загрузка не отправляется сначала в Telegram. Поэтому дальнейшие платформы смогут создавать записи без Telegram.

Большие загрузки и FFmpeg не исполняются внутри webhook/HTTP-ответа. Один рабочий процесс API и один worker могут быть разными процессами из одного backend-образа. Одна PostgreSQL, приватный S3 bucket. Отдельный cron/scheduler используется только там, где нужен существующий реестр maintenance. Не запускать одновременно два несовместимых планировщика.

## 6. Очередь и повторные попытки
Повтор доставки нормален. Inbox уникален по `(bot_id, update_id)`, source mapping по `(bot_id, chat_id, message_id)`. Эти ограничения живут дольше удаления outbox-строк. Нельзя считать краткосрочный dedupe-key outbox вечной защитой от дубликатов.

Событие и enqueue фиксируются в одной транзакции; транзакция завершается до скачивания / кодирования / вызова Telegram. Worker claims используют lease/fencing, heartbeat и срок выполнения. В пилоте одно тяжёлое кодирование одновременно, прочие короткие задания не блокируются длинным видео. Dead letters видны в операционном отчёте; не возвращаются бесконечно в очередь.

Стартовые повторные попытки импорта: 5 с задержками 5, 30, 120, 600 секунд и небольшим jitter; 429 учитывает retry_after. Ошибка формата/превышение лимита — terminal. Пользователь может повторить загрузку; действия публикации защищены idempotency key.

Не обещать exactly-once доставку сообщений ботом: сбой после отправки, но до записи результата может повторить подтверждение. Допустимое последствие — второе подтверждение, недопустимое — второй пост или потеря файла.

## 7. Основа будущих платформ, без реализации сейчас
В БД внутренние user/family/memory/media UUID; внешние identities — `(provider, subject)`. Сейчас реализовать только `telegram`; не добавлять пустые OAuth-драйверы VK/Apple/Google. Привязки существующего аккаунта в будущем только с доказательством владения, не по имени.

Сервер знает права и файлы, клиент получает DTO. API имеет префикс `/api/v1`, обратно совместимые расширения; сервер не должен требовать мгновенного обновления клиента. Независимые действия create/read/edit обеспечивают будущие iOS/Android/VK.

В webapp маленький интерфейс HostBridge: ready, close, back, openBot, getInsets. Реализации сейчас только Telegram и безопасная browser-dev для тестов; browser-dev запрещён в production. Рендерить экраны можно в браузере на synthetic fixtures без Telegram.

Не устанавливать Capacitor, Expo, VK Bridge и не создавать проекты магазинов в этом MVP. Выбор мобильной оболочки — будущая проверка, не зависимость доменной модели. Общий React UI повышает переносимость, но не обещает автоматического превращения в полностью нативный UI.

## 7A. Заменяемый визуальный слой
Визуальный интерфейс остаётся поверх стабильных DTO/use cases: экран не владеет семейными разрешениями, Telegram-идентификацией или storage policy. `docs/mvp/design.md`, `BRANDBOOK.md` и `design/tokens.*` — нормативный контракт UI; React-компоненты реализуют его.

Внешний вид можно существенно менять позднее отдельными UI-задачами без миграции семейных данных и без переписывания bot/backend. Если визуальное решение требует нового поведения, это отдельная продуктовая задача с собственным контрактом и review.

## 8. Масштабирование по измерениям
Сначала измерять очередь, p95 API, объём, CPU FFmpeg, slow SQL. Затем увеличивать ресурсы или worker concurrency; позже горизонтально масштабировать API. Нельзя использовать RAM API как единственную память для приглашений, альбомов и подписи. Квоты, dedupe, sessions и ограничения безопасности должны выдерживать два экземпляра уже в тестах.

Нет Redis, Kubernetes, микросервиса на каждый модуль, собственного event bus, универсальной админки или векторной БД «про запас». Изоляция модулей уменьшает область ревью, но не означает независимый релиз каждого модуля.
