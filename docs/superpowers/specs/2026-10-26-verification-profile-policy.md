# Выбор объёма проверки

Владелец одобрил согласованное изменение правил, классификатора и его регрессий. Задача VERIFY-PROFILE-POLICY, base `7e60ba15b5e42f2bce351c24b806a22c7d4c1613`.

## Подтверждённая причина

Фактический вызов `classifyChanges` для исходного диапазона `6fe2815..7e60ba1` даёт STANDARD; `.autopilot/PROGRESS.md` отдельно уже даёт FAST. Ранее высказанное предположение о повышении профиля из-за журнала оказалось ошибочным. Первоначальный FULL был ручной интерпретацией слов «полный цикл». Дополнительно STANDARD не включал изменённый E2E-файл. Поздняя правка корневого recovery-теста действительно требует FULL.

## Решение

- Команда по умолчанию — `verify:local`; полный цикл задачи означает выбранный по риску профиль, целевые проверки и независимое ревью. FULL — имя отдельного профиля, не синоним тщательности.
- Сохраняются существующие правила чувствительных путей, запрет понижения профиля и отдельные ограничения FRONTEND release. Журнал не требует специального исключения; его поведение закрепляется тестом без исключения всего `.autopilot/`.
- Классификатор возвращает причины по каждому пути. Неизвестный путь или недоступная классификация даёт блокирующее REVIEW_REQUIRED; никакой `--profile`, включая full, его не обходит. После независимого разбора назначение файла фиксируется узким правилом классификации с регрессией. Универсального bypass/receipt API не добавляем.
- Для ручного FULL сверх автоматически требуемого профиля нужен `--reason` с короткой конкретной причиной: явно запрошенный профиль FULL либо подтверждённый риск в diff. «Полное ревью» и «на всякий случай» недостаточны по правилам агента. Автоматический FULL не требует дополнительного аргумента.
- STANDARD добавляет существующие изменённые Playwright specs в план. Dedicated config выбирается по basename, включая `.max-e2e.ts`; Control использует свой config, поддерживаемые MAX specs — MAX config. Неизвестный маршрут spec блокирует план вместо запуска произвольного набора. Удалённые specs не передаются в Playwright; переименование запускает существующий новый файл.
- FULL сохраняет обязательный каталог и также включает изменённые specs: повышение профиля не должно терять сценарий, который STANDARD запускал полностью, из-за фильтра `MAX-FULL:`.
- Перед исполнением выводятся профиль, причины, SHA и команды. Сбой обязательного этапа остаётся FAIL. Побочные неисследованные сбои не превращаются автоматически в новую задачу на ремонт другого модуля.

## Подходы

Поправка только формулировок не предотвращает ручную эскалацию и пропуск E2E. Ослабление всех неизвестных/критических путей до STANDARD теряет защиту. Выбран согласованный вариант: объяснимый автоматический выбор, блокировка неопределённости, причина ручного повышения и целевые E2E.

## Приёмка и границы

Регрессии проверяют журнал FAST, реальный исходный UI-диапазон STANDARD с dedicated MAX-family E2E, чувствительные пути FULL, отказ понижения, блокировку неизвестного пути даже с явным FULL, причины CLI до запуска, маршрут E2E и отсутствие нулевого/пропущенного успешного результата. Production-код приложения, данные, deployment allowlist и старый draft PR #254 не изменяются.

Сам verifier остаётся критическим путём. Для этой правки применяется текущий обязательный gate; известные baseline-сбои фиксируются отдельно, без обхода или автоматического расширения задачи. Dry-run доказывает состав плана, но не PASS его тестов.
