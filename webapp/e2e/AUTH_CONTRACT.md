# Browser E2E auth contract

`bun run e2e:webapp` exercises the production host sign-in path. The host supplies signed Telegram `initData`; the browser exchanges it at `/api/v1/auth/telegram`. The server does not mount `/api/auth/register`, `/api/auth/login`, or the password reset routes in production. The optional legacy router exists only for backend regression tests (`legacyPasswordAuthForTests`), and the production app refuses to mount it.

The former browser specs `auth.spec.ts` (6 cases), `avatar.spec.ts` (2 cases), and `rbac.spec.ts` (2 cases) required the removed password signup/login UI and admin account workspace. All ten cases tested that test-only legacy surface and were removed from the production browser acceptance command. They were not skipped. Legacy password/session behavior remains covered by `backend/src/modules/auth/auth.integration.test.ts`; legacy administrator account/role behavior remains covered by `backend/src/modules/users/users.integration.test.ts`. Those backend suites explicitly mount the test-only router. The old personal-avatar browser journey is not a supported production screen; the supported child-photo browser journey is covered by `specs/family.spec.ts`.

Production authentication remains exercised end to end by `feed.spec.ts` and `specs/family.spec.ts`, including signed Telegram exchange, admitted and unadmitted users, sessions, family roles, and API guards. `backend/src/modules/auth/telegram-auth.integration.test.ts` verifies that forged Telegram data is rejected and legacy public routes return 404. Any future browser auth cases should start from a supported host identity rather than password signup.
