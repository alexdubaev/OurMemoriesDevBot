## Configuration / minimal seam

- `backend/src/env.ts`: `TELEGRAM_ENABLED` controls `validateTelegramEnv`. When false, a configured `TELEGRAM_BOT_TOKEN` is rejected as ignored; when true it requires token + valid `TELEGRAM_INBOX_ENCRYPTION_KEY`, production webhook mode, and in webhook mode HTTPS URL and webhook secret. This flag therefore cannot express auth-only Telegram.
- `backend/src/index.ts` calls `startTelegramIfEnabled` before serving HTTP. `backend/src/telegram-startup.ts` calls Telegram `getMe`, then constructs `createTelegramModule`; any failure closes runtime and aborts backend. The same module owns webhook routes and polling (`index.ts`). This causes network dependence and bot lifecycle for auth when enabled.
- Auth is already an independent HTTP/module path: `backend/src/app.ts` always creates/mounts auth routes; `backend/src/modules/auth/index.ts` always builds `TelegramAuthService`. `backend/src/modules/auth/transport/routes.ts` exposes `POST /api/v1/auth/telegram`. `buildTelegramAuthService` only needs `env.TELEGRAM_BOT_TOKEN` to verify incoming initData; it never calls Telegram API or needs webhook, inbox key, webhook secret, or API routes. So runtime toggle alone cannot restore login; current env schema blocks retaining token with `TELEGRAM_ENABLED=false`.
- Minimal intended boundary: decouple “Telegram auth configured” from “Telegram bot message lifecycle enabled” in env validation/startup; auth should use configured token for HMAC, while `TELEGRAM_ENABLED` remains the existing lifecycle toggle. Keep bot `getMe` only on lifecycle start. Do not make auth verification conditional on bot startup. No existing supported config achieves this without code; enabling `TELEGRAM_ENABLED` activates webhook/polling requirements and startup `getMe`.

## Security / data invariants to preserve

- `backend/src/modules/auth/infrastructure/telegram-init-data.ts`: unique query fields, Telegram WebAppData HMAC via bot token, constant-time hash comparison, auth_date freshness/future tolerance, canonical numeric subject, SHA-256 replay fingerprint (raw initData/signature not stored).
- `backend/src/modules/auth/application/telegram-auth-service.ts` and `infrastructure/auth-repository.ts`: replay fingerprint is single-use except same-session replay; one transaction binds/creates the session and replay row. `ExternalIdentity(provider, subject)` is unique; Telegram login provisions/uses provider identity and session, not account linking.
- `backend/src/modules/auth/telegram-auth.integration.test.ts` covers HttpOnly refresh cookie, no token in JSON, provider identity, foreign replay rejection, same-session replay, refresh preserving identity, forged data rejection. `max-auth.integration.test.ts` also verifies Telegram and MAX identities remain separate.
- Frontend handoff/session race surface: `webapp/src/features/auth/api.ts` auth epoch, refresh single-flight/recovery guards; `webapp/src/features/auth/host-auth-handoff.ts`; `webapp/src/features/app/telegram-auth-handoff.ts`; wiring in `webapp/src/App.tsx`. Preserve epoch checks and private query/session invalidation. No account linking/automatic merge is present in this auth flow and must not be introduced.
