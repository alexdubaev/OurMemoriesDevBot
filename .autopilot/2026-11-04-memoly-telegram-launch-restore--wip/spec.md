# Спецификация: восстановление Telegram-входа memoLy

## Задача

Существующий @OurMemoriesDevBot должен открывать memoLy по уже исправленному владельцем адресу и выдавать обычную защищённую сессию memoLy по проверенным данным Telegram. Пользователь получает существующий семейный интерфейс в пределах своего действующего членства. Возврат приёма сообщений, webhook и связывание аккаунтов в задачу не входят.

## 1. Существующий бот и секрет

Использовать только токен существующего бота из защищённого хранилища. Read-only getMe с рабочего компьютера подтвердил username OurMemoriesDevBot; токен не выводился и не записывался. В защищённом файле сохранены также прежние webhook/inbox ключи, но они не нужны для входа и не активируются. Read-only getWebhookInfo: webhook отсутствует, pending=0. Отдельная menu button ещё указывает на старый стенд: владелец отдельно разрешил изменить только её URL на https://app.memoly.ru/, сохранив текст и webhook; Main Mini App URL уже обновлён самим владельцем.

## 2. Минимальное восстановление входа

Добавить отдельный необязательный серверный секрет `TELEGRAM_AUTH_BOT_TOKEN`: его наличие явно разрешает только уже существующий exchange Telegram initData. Существующий `TELEGRAM_ENABLED=false` продолжает отключать жизненный цикл message-бота, startup getMe, polling и webhook routes; существующие требования к включению message-бота не ослаблять. Legacy `TELEGRAM_BOT_TOKEN` сохраняется для прежнего режима включённого бота. При одновременной настройке токены должны совпадать; несовпадение — ошибка конфигурации. Если оба отсутствуют, exchange остаётся закрытым.

Проверка подписи остаётся локальной на backend: HMAC, constant-time, уникальные поля, auth_date, replay и привязка к подтверждённому Telegram subject. Никакого Telegram API-запроса на каждый вход или обхода подписи. Сессии, HttpOnly refresh cookie, Origin, refresh rotation, отзыв и привязка external identity сохраняются. Новых API, схемы и миграций нет. Повторный вход использует существующую внешнюю идентичность. Имя, фотография и совпадающий числовой MAX subject не объединяют пользователей.

## 3. Семья и медиа

Действующая Telegram-идентичность получает только членства своего userId. Проверить отсутствие автоматического доступа к семье MAX-пользователя, доступ обычного принятого участника, запрет чужой семьи и отказ после отзыва. Синтетические fixtures задают членство только в изолированной test БД; production membership/roles вручную не назначать.

Фото в ленте и карусели загружаются через обычную authenticated media цепочку. MAX-видео: MaxVideo → защищённый media endpoint memoLy с семейным guard → MAX API для текущего rendition → MAX CDN с GET/HEAD/Range. Источник входа зрителя не меняет этот guard. В browser journey проверить запуск, паузу, перемотку, продолжение, фото-карусель; звук только с fixtures, содержащими аудиодорожку. Telegram-hosted video handoff — отдельный механизм, не выдавать его за MAX playback. Ни MAX SDK, ни собственный Telegram Bot API Server не добавлять.

## 4. Изолированные проверки

Реальная PostgreSQL `*_test`, отдельные storage/порты, только синтетические bot secrets/initData/provider media. Узкие config/auth integration проверяют auth-only режим при выключенном message-боте, forged/expired/replayed payload, provider separation, refresh и family/media ACL. Browser сценарий запускает настоящий React и Telegram host bridge с синтетическим подписанным initData; внешние provider-сервисы в нём подменяются на тестовые endpoints. Негативные пути не подменять успешными ответами. Затем один применимый canonical FULL на точном candidate source и одно независимое technical review; после confirmed fixes — affected checks, без повторов чистого review.

## 5. Безопасная доставка и восстановление

PR, FULL и guarded Selectel release ниже — обязательные ограничения актуального AGENTS.md и docs/DEPLOYMENT.md, а не новые продуктовые возможности. Ревизии и обнаруженные настройки бота — проверенные операционные факты из notes.md.

Одна временная ветка от f70448a0 и один PR; publication/merge/deploy разрешены назначенным владельцем заданием. Выполнить существующие gates и guarded Selectel release. Новую миграцию не создавать, обязательные guards/backup/readiness/S3 не менять и не обходить. Повторно сверить актуальные main и production. Новый секрет загружается только в защищённый runtime env, не в Git/образ/командные аргументы.

Обоснование отдельного auth-only имени: прежний совместимый runtime должен игнорировать новый необязательный ключ и продолжать запуск с TELEGRAM_ENABLED=false. Настройка старого TELEGRAM_BOT_TOKEN при этом флаге сломала бы его конфигурационную проверку. До promotion проверить это с реальным designated recovery source/образом. Сохранить защищённую копию изменяемого env и возможность вернуть точную прежнюю конфигурацию. Если существующий recovery gate требует нового защищённого разрешения, сначала установить применимость и подготовить конкретное доказанное решение; не ослаблять guard.

D01 (при таске 01): source helper на чистом 1675b040 показал новый executable fingerprint 2cd72b36e5fb2ccd01b9533d353419931ccf8d62d919c63a79e29c283b59a63f; действующий recovery registry знает предыдущий точный source, поэтому новый runtime сам по себе в него не входит. Подготовить только точную привязку этого измеренного source к уже принятому s3-album-social recovery profile и той же immutable паре 26cfab9c. Никаких новых target/profile, расширения диапазонов или обхода checks. Обязателен regression: точный source разрешён, изменение production blob после него отклонено; все прежние SQL/S3/lock/image guards остаются. Это необходимая metadata часть уже разрешённой безопасной доставки, не новое правило восстановления. На реальном designated recovery image отдельно подтверждено configAccepted=true при новом синтетическом auth-only ключе, явном TELEGRAM_ENABLED=false и отсутствии legacy token, без сети и подключения к БД.

D02 (при таске 01): canonical verifier dry-run остановился с REVIEW_REQUIRED до запуска проверок на трёх новых точных путях: архивный snapshot предыдущего Autopilot state.js, корневой .env.example и dedicated Telegram Playwright config. После содержательного разбора все три — metadata/config/test infrastructure текущей защищённой auth-задачи. Добавить только эти три literal identities в существующий REVIEWED_FULL_PATHS, с regression требуемого FULL и сохранения отказа для соседних новых путей. Это повышение до FULL, не понижение, skip, wrapper или широкая allowlist. Алгоритмы классификатора, unknown-path отказ и запрет CLI downgrade сохраняются.

## 6. Реальный запуск и приёмка

После выкладки проверить фактический runtime/image/env (только имена и булевы признаки), public readiness и реальный Telegram Desktop запуск Main Mini App. Не отправлять /start или другие сообщения. Физический iPhone не объявлять проверенным по desktop Chromium/WebKit. Фото/MAX CDN на production проверять только в действующей семье через обычные права реального пользователя; не создавать тестовые production семьи, не подписывать административную сессию и не добавлять себе членство. Если законного семейного доступа в Telegram ещё нет, это отдельная явно указанная граница фактической приёмки, а не выдуманный PASS; синтетический family/media сценарий должен быть выполнен.

## 7. Вне рамок и ограничения

Не связывать и не объединять MAX/Telegram аккаунты. Не менять membership/roles административно. Не создавать нового бота, webhook или Telegram Bot API Server. Не отправлять реальные сообщения. Разрешено изменить только URL menu button на https://app.memoly.ru/ по отдельному ответу владельца. Остальные настройки бота не менять; Main URL уже изменён владельцем. Не менять accepted UI, данные, S3 storage и deployment guards. Не просить и не показывать секреты. Не возвращать Telegram capture, отправку или notifications.
