## Риски / ловушки
- R1 `Memory.childId` NOT NULL + FK Restrict. «Ноль детей на воспоминание» и «много детей» требуют новой связи (таблица тегов) и/или смягчения NOT NULL (contract-фаза, отдельным релизом; старый рантаймс всё ещё пишет childId). Удалять Child с воспоминаниями нельзя (Restrict), `Album.childId` и `MaxVideoUploadSession.childId` тоже Restrict: удаление профиля ребёнка нужно спроектировать (что с тегами, альбомами `year/events/workshop`, MAX-сессиями, аватар-ассетом).
- R2 Жёсткие `children[0]`/`take: 1` в: family-service.ts (124,147,329-331,473,538,597), bot-family-target.ts (20,34), max/source-target.ts (65-80), prisma-album-repository нет. Для семьи с 2+ детьми `getFamily`, `getFamilies`, `createInvite`, `setupStatus`, `capabilities.canPublish*` смотрят только на самого раннего ребёнка; `completeChildProfile` и `PUT /child` всегда перезаписывает первого (нет пути «добавить второго»).
- R3 `FamilyResponse.child` (один) и `childSchema.isComplete` используются в `App.tsx` как гейт приложения: 744 `!familyResponse.child` -> onboarding вместо приложения; 759-762 рендер вкладок только при наличии `familyResponse.child`; `FamilyScreen`, `FamilyPresentation`, `AlbumsPage`, `ComposerHost`, `useChildAvatar` ждут одного ребёнка. Изменение формы ответа ломает persisted cache (`validatePresentation` -> `familyResponseSchema.safeParse`).
- R4 Авто-назначение единственного ребёнка: все серверные импорты (`bot-family-target.ts`, `max/infrastructure/source-target.ts`, `resolveChannelTarget`, `process-*.ts`, direct video finalize) должны заменить «выбери ребёнка» на «теги по правилу: 1 ребёнок -> тег, 2+ -> без тега». `MaxSource.childId` и `choiceCandidates[].childId` используются как «цель публикации» и пишутся обратно в `MaxSource` (без FK); публикация `SourceMemoryInput.childId` обязательна, повторная публикация сверяет childId (invalid_input при расхождении) — при смене семантики идемпотентность повторов MAX надо сохранить.
- R5 Пофото/повидео теги: вложения имеют три разных источника и разные id (MediaAsset.id / MaxVideoReference.id / TelegramVideoReference.id), общая `position` не в DTO; `MemoryMedia.mediaId` unique; MAX-видео в режиме `attachment` связывается сессией (`session.childId === input.childId`, prisma-memory-repository.ts:154) — с несколькими детьми условие ложно сработает/сломает вложение. Для голоса/заметки тег на всё воспоминание.
- R6 Курсоры: `childId` уже в подписи (`memory-cursor.ts`), для фильтра «Без отметки» понадобится новое значение фильтра в курсоре (version 2/3 -> совместимость со старыми курсорами, TTL 15 мин). `findPage`/`findUnreadPage` фильтруют по `Memory.childId`; индекс по childId отсутствует; для тегов по вложениям нужен join/exists и индекс.
- R7 Контракты strict: `memoryDtoSchema.strict()`, `createMemoryRequestSchema` (`childId` обязателен в `memoryBaseInputSchema`), `familyResponseSchema.strict()`; новые обязательные поля ломают старые клиенты, MAX-прокси и persisted cache (`memoryPageSchema.safeParse` в `validatePersistedState` — один несовпавший элемент отбрасывает всю ленту из кэша; допустимо, но тест `private-cache.test.ts` нужно обновить). Новые поля делать optional/default либо поднять `PRIVATE_CACHE_SCHEMA`.
- R8 Ключи запросов: `feedQueryKeys.list` позиционный (8 элементов, [3]=filter, [4]=unreadOnly, [5]=accountId, [6]=membershipEpoch). `matchesReactionFeedScope`, `isPersistableQueryKey` (length===8), `removePrivateFamilyQueries` зависят от позиций. `FeedFilter` в webapp = вид контента (`photo|video|...`), а не ребёнок; не смешивать (`PersistentFamilyPresentation.filter` валидируется 5 значениями; для childFilter добавить отдельное поле и расширить `validatePresentation`). Сейчас FeedPage игнорирует `filter` (`void filter`).
- R9 Права: edit/delete = любой `full` (не только автор), `viewer` не редактирует; теги: «only full редактируют теги, теги не дают права edit/delete» уже соответствует существующей модели — нужен новый `requireFull`-метод и PATCH-контракт (сейчас PATCH тела памяти не принимает ничего кроме body/occurredAt/expectedVersion; `version` растёт при любой правке — решить, поднимает ли смена тегов версию воспоминания и влияет ли на unread order (`unreadOrderVersion` меняется только при смене occurredAt)). Контент ребёнка-аватара: `child_avatar` загружает только владелец (`media-service.ts:32`), доставка идёт через `avatarForChildren` — для нескольких детей работает без изменений (по одному `@unique avatarMediaId`).
- R10 Альбомы: partial unique «один live year на ребёнка» уже есть; `listAlbumsQuerySchema` и подписанный курсор альбомов без childId; `AlbumsPage` и `AlbumForm` рассчитаны на одного `child` (создание: `child!.id`). Страница ребёнка = фильтр по `AlbumDto.childId` (без free-альбомов, у которых childId null — решить, показывать ли).
- R11 Две версии UI (`legacy` и `v2` по `VITE_MEMOLY_UI_VERSION`): `ChildHeader.tsx` и `ChildHeaderV2.tsx` дублируют разметку; `onOpenChild` в ленте работает только в v2 для владельца. Новый заголовок семьи с аватарами и чипами нужно сделать под обе версии либо явно зафиксировать, какая актуальна (AGENTS: принят «memoLy UI v4»; в коде нет такой переменной — проверить `ui-version.ts`: только `legacy|v2`). Иконки: только WebP RGBA, SVG запрещены (AGENTS §11).
- R12 Тестовые сиды и фабрики (~20 integration тестов, e2e сиды, `development-seed.ts`) создают одного ребёнка и вызывают `children[0]`-логику; `PUT /child` как единственный способ «завершить» ребёнка используется в onboarding и тестах. Любой новый маршрут `/families/:id/children` должен сохранить обратную совместимость `PUT /child` и `child` в `FamilyResponse` на время релиза (expand-фаза).
- R13 Деплой: схема/контракты/ACL => FULL, backend не должен переписываться «frontend-only» путём; при релизе старый рантайм продолжает писать `childId` — миграции должны оставаться expand (добавление таблицы тегов + бэкфилл), без `DROP/SET NOT NULL` в том же релизе.
